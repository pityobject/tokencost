## 一、技术报告结构（2 页，不要超过）

**第 1 页（决定别人要不要看第 2 页）**

| 段落 | 字数 | 内容 | 常见错误 |
|---|---|---|---|
| 标题 | 1 行 | LLM 推理服务的成本—延迟—质量 Pareto 前沿：一个可被实测证伪的解析模型 | 起名"某某的设计与实现"（无信息量） |
| 一句话结论 | 60 字 | 用 12 个标定点预测 40 个未见配置，单位成本误差 5.3% | 开头写背景不写结论 |
| 图 1 | — | TPOT 与权重大小的过原点直线（证明访存受限） | 图太小、没有图注 |
| 方法 | 150 字 | 两条公式 + 三个参数 + 12 点标定 + 留出验证 | 只写"我用 roofline 模型"不讲怎么验 |
| 关键结果 | 100 字 + 表 | MAPE / 最大误差 / 覆盖率 / regret / 成本降幅 | 只报最好那个数 |

**第 2 页（给想深挖的人）**

| 段落 | 内容 |
|---|---|
| 实验设置 | 机器、软件版本、60 格网格、测量纪律六条 |
| 图 2–4 | 吞吐-并发、成本-并发、预测 vs 实测 |
| 残差分析 | 误差随哪个维度变大，适用域限定在哪 |
| 局限 | 8 GB 单卡、任务集规模、未测分布式；**主动写局限不会扣分，会加分** |
| 复现 | 仓库链接 + 三条命令 |

### 关于"主动写局限"

这是很多人不敢做的事，但它是**可信度的来源**。模板：

> 本文结论基于单张 8 GB 移动端 GPU 与 256 token 输入、128 token 输出的负载画像。
> 在长上下文（>8k）或高并发（>32）下模型未经验证，且未考虑多卡/多租户干扰。
> 迁移到 A100 或昇腾 910B 时，模型结构不变，但需要重标定两个机器常数（有效带宽、有效算力）。

## 三、一页《从单机到集群》（最高杠杆，2 小时就能写完）

面试时递出去的一张纸。三栏，回答同一个问题："你这套东西，到我们这里怎么用？"

| | 鹏城实验室（云脑算力） | 华为（昇腾推理） | 字节（推理成本） |
|---|---|---|---|
| **我的"选配置"对应你们的** | 调度器的实例分配 + 准入控制 | 卡型选择 + 量化档位 + 槽位数 | 实例规格选型 + 扩容策略 |
| **我的"成本下界"是你们的** | 集群 GPU 秒 / 完成请求数 | 单卡每 token 吞吐上界 | 每百万 token 成本 |
| **我的"SLA 约束"是你们的** | 多租户 P99 隔离 | 推理服务 SLA | 线上 P99 延迟预算 |
| **只需重标定两个数** | 有效带宽、有效算力 | 同左 + kernel 效率因子 | 同左 |
| **模型要升级的地方** | 从"选配置"升级为"选配置 + 排队网络 + bin packing" | 把 roofline 换成 CANN 实测曲线 | 接入 A/B 平台做在线验证 |
| **我下一步能立刻做的** | 用云脑公开论文参数做外推实验 | 读 MindIE 的性能报告做对照 | 用剪枝后模型验证小模型够不够用 |

> **为什么要写这一页**：所有评委的默认怀疑是"学生项目跟我们有什么关系"。
> 这一页就是把这句话提前回答掉。它不需要任何额外实验，只需要 2 小时想清楚。

## 五、10 分钟讲稿（背下来，说慢一点）

```
【0:00–1:00】问题
  "大模型每吐一个字，都要把整个模型从显存里读一遍。
   所以在 8 GB 的笔记本上，'推理有多贵'其实只取决于两个数：
   这台机器读得有多快、算得有多快。"

【1:00–3:00】方法
  "我把这两个数写成两条公式，一共三个参数：有效带宽、有效算力、固定开销。
   关键洞察是：decode 阶段是读显存受限，不是算力受限——
   所以加并发能摊薄成本，但过了拐点就没用了。"

【3:00–6:00】验证（这一段最重要）
  "我只用 12 个配置点去拟合，然后让它预测它没见过的 40 个点。
   单位成本误差 __%，最差 __%，而且我给的 90% 预测区间实测覆盖率是 __%。
   这个覆盖率是关键的：如果它只有 60%，说明我过度自信；
   如果它 99%，说明我的区间宽得没信息量。"

【6:00–8:00】结果
  "把它做成推荐器后，输入延迟和质量的约束，3 秒给出配置。
   和事后用全量实测选出的最优比，后悔值只有 __%；
   相对大家常用的默认配置，成本降了 __%。"

【8:00–10:00】局限与延展
  "局限是单卡 8 GB、负载画像是 256 进 128 出。
   但模型结构跟硬件无关：搬到 A100 或昇腾上，只要重标定两个机器常数。
   我写了一张纸，说明这套方法怎么接到云脑的调度、昇腾的选型和字节的容量规划上。"
```

**练习方法**：录音、回放、计时。三次之后你会发现自己每次都在删同一句废话——那句就是该删的。

## 六、12 个高频追问（每题 40 秒内答完）

| # | 问题 | 答案要点 |
|---|---|---|
| 1 | 成本怎么定义？为什么不用 $？ | GPU 秒/百万 token（硬件无关），$ 只作敏感性分析 |
| 2 | 为什么只有 3 个参数？ | 简约性；每多一个参数解释力就少一分；且 12 个点撑不起更多参数 |
| 3 | 为什么用对数比做损失？ | 相对误差、对称、跨两个数量级 |
| 4 | 12 个点够吗？ | 参数/数据比 1:4；且 DOE 覆盖了各维度的极端与中心 |
| 5 | 预测区间怎么来的？ | 两层：残差自由度校正 + 格内重复噪声/√k；用 t 分布不用正态 |
| 6 | 覆盖率为什么必须落在 82–96%？ | 太低=过度自信；太高=区间无信息量 |
| 7 | 换张显卡还能用吗？ | 结构不变，只需重测带宽与算力两个常数 |
| 8 | 为什么用 CVaR 不用 P99？ | 样本量不足 + P99 不可优化；CVaR 凸且稳定 |
| 9 | 后悔值是什么？ | 推荐成本/事后最优成本−1；衡量决策质量而非模型精度 |
| 10 | 拐点怎么来的？ | 令 t_mem = t_cmp，得 b* = w·PEAK/(2·BW)；实测与预测偏差 __% |
| 11 | 你最大的失误是什么？ | **见下一节，必须是真事** |
| 12 | 给你三个月继续做什么？ | ① 双卡/多租户干扰建模 ② 排队网络升级 ③ 上线 A/B 验证 |

### 第 11 题的答案（必须真实，且要说清"怎么发现的"）

备选（做完实验才知道哪个是你的）：

- **"我原以为并发过拐点后成本会上升，实测发现只是趋平——因为 TPOT 涨了但吞吐没涨，两者的比值消掉了。"
  这个发现让我把结论从'别开太大并发'改成'开太大并发不省钱，只会让延迟变差'。"**
- **"我第一次测出来 7B 的带宽只有 3B 的一半。后来发现 7B 有 8 层被塞到了 CPU，
  日志里 `CPU model buffer size` 不是 0。教训是：先看日志的显存分配，再相信自己的数据。"**
- **"我一开始用样本内残差估预测区间，覆盖率只有 68%——我的区间太窄，等于过度自信。
  改成两层误差 + t 分布后，覆盖率到了 __%。这件事让我明白'给自己的不确定度也得做验证'。"**

## 概念 1：token 是什么

模型不是按"字"处理的，是按 **token**（词元）。中文大致：

- 1 个汉字 ≈ 0.6–0.7 个 token
- 1 个英文单词 ≈ 1.3 个 token
- 100 个汉字的一段话 ≈ 65 个 token

**为什么你必须知道这个**：所有性能指标都是"每个 token 多少毫秒"，所有成本都是"每百万 token 多少钱"。把 token 和字数混了，你的成本会算错 40%。

---

## 概念 2：一次推理分两个阶段（这是全项目的骨架）

```
  你的问题（256 个 token）
        │
        ▼
  ┌─────────────────────────┐
  │ ① PREFILL（预填充）      │  一次性把 256 个 token 全算一遍
  │    · 主要是矩阵乘法       │  → 算力密集（compute-bound）
  │    · 很"胖"，能并行      │  → 产出：第一个 token
  └─────────────────────────┘
        │
        ▼  第一个字出现（这段时间叫 TTFT）
  ┌─────────────────────────┐
  │ ② DECODE（解码）         │  一个一个往外蹦
  │    · 每蹦一个都要把       │  → 带宽密集（memory-bound）
  │      全部权重读一遍       │  → 每个 token 的时间叫 TPOT
  └─────────────────────────┘
```

**关键洞察（请背下来）**：

> **Prefill 花钱在"算"，Decode 花钱在"读"。**
> 所以优化 prefill 要用更快的算力（更大 batch、更低精度矩阵乘），
> 优化 decode 要**减少要读的字节数**（量化、更小的模型）。

这也是为什么你的项目能做成：decode 阶段的时间几乎只取决于"权重有多大 / 显存带宽多快"，而这两个数你都能测。

## 概念 3：KV cache（为什么第二个 token 比第一个快得多）

**问题**：生成第 2 个 token 时，模型要"回头看"前面所有 token 的信息。如果每次都重算一遍，第 N 个 token 就要算 N 次，总体是 O(N²)。

**做法**：把每层算过的 Key 和 Value 存起来（就是 KV cache），下一个 token 只算新的那一个，直接查表。总体从 O(N²) 降到 O(N)。

**代价**：吃显存。这是 8 GB 显卡上最硬的约束。

**你需要会算的一个数**：每个上下文 token 占多少 KV 内存？

```
每层每 token 字节数 = 2（K 和 V） × KV头数 × 头维度 × 2（fp16 每数 2 字节）
```

| 模型           | 层数  | KV 头数 | 头维度 | 每 token   | 8192 上下文时 |
| ------------ | --- | ----- | --- | --------- | --------- |
| Qwen2.5-1.5B | 28  | 2     | 128 | 28 KB     | 0.23 GB   |
| Qwen2.5-3B   | 36  | 2     | 128 | 36 KB     | 0.30 GB   |
| Qwen2.5-7B   | 28  | **4** | 128 | **56 KB** | 0.47 GB   |

**所以 8 GB 卡的账是这样的**（7B-Q4、8192 上下文、16 并发）：

```
4.68 GB（权重） + 16 × 0.47 GB（KV） + 0.6 GB（其他） ≈ 12.8 GB  >  8 GB   ✗ 装不下
```

**这句话就是 S0 里那张"可行性表"的来源，也是你报告里"非矩形可行域"的物理解释。**
`tc_config.py` 里的 `estimate_vram_gb()` 干的就是这件事。

## 概念 4：量化（Q8 / Q4 到底在做什么）

模型权重原本是 16 位浮点（fp16），每个数 2 字节。量化就是**用更少的位来表示它**：

| 量化     | 每个权重     | 7B 模型权重 | 相对 fp16 |
| ------ | -------- | ------- | ------- |
| fp16   | 2 字节     | 15.2 GB | 1×      |
| Q8_0   | ≈1.06 字节 | 8.1 GB  | ↓ 47%   |
| Q4_K_M | ≈0.61 字节 | 4.7 GB  | ↓ 69%   |

**注意措辞**：量化不是让"计算变快"，而是让**要读的字节数变少**。
在 decode 阶段（读显存受限），读的字节少了，时间就按比例少了。
这就是为什么"Q4 比 Q8 快 2 倍左右"，而它们在算力上根本没有区别。

代价是**精度损失**。损失多大？你的项目要用固定 200 条任务集去测（S7 篇会讲），而不是拍脑袋说"Q4 也够用"。

## 核心练习：用两次测量反推同一个带宽

这是本阶段的重头戏。**动手做，不要只看结论。**

### 步骤 1：量 7B-Q4

```powershell
cd D:\llm\bin
.\llama-cli.exe -m D:\llm\models\qwen2.5-7b-instruct-q4_k_m-00001-of-00002.gguf -ngl 99 -p "请用一句话介绍你自己。" -n 64 -st
```

记下最后那行里的 **Generation** 数值，记为 **P7**。
在 4060 Laptop 上，7B-Q4 的实测值约 **45–55 t/s**。

### 步骤 2：量 3B-Q4

```powershell
.\llama-cli.exe -m D:\llm\models\qwen2.5-3b-instruct-q4_k_m.gguf -ngl 99 -p "请用一句话介绍你自己。" -n 64 -st
```

记为 **P3**。3B-Q4 的实测值约 **90–110 t/s**。

### 步骤 3：算带宽（手算，写到纸上）

```
有效带宽 ≈ 权重字节数 × 每秒生成 token 数
```

|       | 权重字节     | × 你的 tok/s  | = 有效带宽      |
| ----- | -------- | ----------- | ----------- |
| 7B-Q4 | 4.683 GB | P7 = ______ | ______ GB/s |
| 3B-Q4 | 2.105 GB | P3 = ______ | ______ GB/s |

### 步骤 4：判断

- 两次结果**相差 15% 以内** → 说明"时间正比于权重字节"成立，**访存受限确认**。你已经拿到了本项目的第一个核心结论。
- 差很多（比如 2 倍）→ 常见原因：① 7B 有部分层被塞到 CPU（看日志里有没有 `CPU` buffer）；② 第一次跑还没预热；③ 笔记本降频（插电、开高性能模式再试）。

### 为什么要做这一步

面试时最容易被问倒的是"你这个结论有证据吗"。这个练习给你的证据形式是：

> **"我用两种不同大小的模型分别测了速度，反推出来的带宽几乎一样（___ GB/s）。
> 这说明时间确实由访存量决定，而不是由算力决定。这就验证了 decode 是 memory-bound。"**

这比说"我看书上说是 memory-bound"强一百倍。

### 进阶：为什么两个带宽会差 10% 左右（这一步能让你在面试时多讲 30 秒）

实测手算结果（2026-10-19，这台机器）：

|       | 权重       | P        | 朴素算法 `W÷(1/P)` |
| ----- | -------- | -------- | -------------- |
| 7B-Q4 | 4.683 GB | 50.7 t/s | 237.4 GB/s     |
| 3B-Q4 | 2.105 GB | 99.3 t/s | 209.0 GB/s     |

相差 12.7%。**不要把它当成噪声抹掉**，它指向模型里缺了一项：每 token 的**固定开销**。

假设两个模型都有同一个固定开销 `c`（采样、调度、请求解析）：

```
4.683 / (19.72 − c)  =  2.105 / (10.07 − c)
```

解出 `c ≈ 2.19 ms`，此时两个模型都指向 **267.1 GB/s**——完全重合。

**三个结论**：

1. **==这块 4060 Laptop 的有效带宽约 267 GB/s，对应标称 272 GB/s 的 98%。
   （我原先按 256 估是偏保守的；`tc_config.py` 里不写死标称值，正是这个原因。）==**
2. ==**小模型被固定开销拖累更狠：`c` 占 3B 的 22%、占 7B 的 11%——这就是为什么朴素算法对 3B 偏低。**==
3. ==**这个 `c` 就是 S5 模型里的第三个参数 `ovh`。你现在是在没有公式的情况下，靠两次测量把它"摸"出来的。**==

> **==必须同时说清的限制：两点数据定两个未知数，是恰好唯一解，不算证明——任何两点都能被完美拟合。
> 真正的定标要等 S5 的 12 个点、3 个参数、68 个留出格。手算的价值是发现第三个参数存在且量级 2 ms，
> 而不是"算出了带宽"。这个区分，面试时能体现你是真懂统计。==**

## 顺便学会读 llama-cli 的日志

跑上面命令时，输出里这几行请认一下：

b11669 这个 build 的输出和老版本不一样，按下面这张表认（实测过的）：

| 你屏幕上会看到的                                                         | 含义                                                    |
| ---------------------------------------------------------------- | ----------------------------------------------------- |
| `[ Prompt: 1291.7 t/s \| Generation: 100.9 t/s ]`                | **最重要的那行**：Prompt = prefill 速度，Generation = decode 速度 |
| `I load_tensors:        CUDA0 model buffer size =  1834.83 MiB`  | 权重在显存里占多少（要加 `-lv 4` 才显示）                             |
| `I load_tensors:   CPU_Mapped model buffer size =   166.92 MiB`  | mmap 的主机副本，**不算显存**                                   |
| `I sched_reserve:  CUDA_Host compute buffer size =    48.02 MiB` | 计算缓冲区                                                 |
| `n_ctx_slot = 2048, n_slots = 16`                                | 每槽位上下文、槽位数（在 server 日志里）                              |

> **`--perf` 不再产生旧式 `llama_perf_context_print` 块**（那是老版本）。
> 现在 decode 速度就在 `Generation: ... t/s` 里。
> 你在本阶段量的 P7/P3 就是 **Generation** 那个数。
> 想看显存分配细节，加 `-lv 4`；想让它跑完一轮就退出，加 `-st`（`-no-cnv` 在这个版本不存在）。

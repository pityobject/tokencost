### 表 1 怎么读

| 列 | 含义 |
|---|---|
| `ttft_p50_ms` | 这一格"典型"的首字延迟 |
| `tpot_p50_ms` | 这一格"典型"的出字间隔 |
| `throughput_tps` | 整机每秒吐出多少 token |
| `cost_gpu_s_per_1m` | 每百万 token 占多少 GPU 秒 ← **越低越好** |
| `temp_c_median` / `clock_sm_median` | 当时的温度与核心频率 |
| `n_repeats` | 这一格跑了几轮（应该都是 3） |

### 表 2 是你最直接的结论来源

它算的是"同一个模型、从最小并发到最大并发，成本降了几倍"。比如：

```
3B q4_k_m ctx=512  并发 1→32：成本 12122 → 407（降为 1/29.8），TPOT 12.0 → 12.7 ms
```

**这句话的意思是**：并发从 1 加到 32，单位成本降到 1/30，而**单条请求的延迟几乎没变**（12.0 → 12.7 ms）。
这就是批处理的价值，也是所有推理服务要"攒批"的原因。

> 如果你的数据里 TPOT 在高并发时**明显上升**（比如翻倍），也有意义：说明碰到了别的瓶颈（显存压力、调度开销）。
> 这也是好结论，写清楚就行——**不要为了让曲线好看去删数据。**

## 二、三个图分别说明什么

### 图 1 `fig1_throughput_vs_concurrency.png` —— 并发 vs 吞吐

- 横轴并发（对数），纵轴 tokens/s，每个上下文一张小图。
- **该看到的**：吞吐随并发近似线性上升，然后逐渐变缓。
- **物理解释**：一开始每加一条序列，就多摊薄一次权重读取（白赚）；接近算力上限后，加并发不再提高总吞吐。
- 这张图回答："**我的机器最多能同时服务多少人**"。

### 图 2 `fig2_cost_vs_concurrency.png` —— 并发 vs 单位成本

- 纵轴对数。**该看到的**：曲线一路下降，然后趋平。
- **趋平的位置就是"最优点"**：再多加并发，成本不再降，但延迟会变差。
- 这张图回答："**攒到多少批最划算**"——这是容量规划的核心问题。

### 图 3 `fig3_tpot_vs_weights.png` —— 出字时间 vs 权重大小

- 横轴权重 GB，纵轴 TPOT（并发 1）。
- **该看到的**：几个点几乎落在一条**过原点**的直线上。
- **物理解释**：时间 ∝ 要读的字节数 ⇒ 瓶颈是带宽，不是算力。
- 斜率倒过来就是有效带宽：`1000 / 斜率`。
- 这张图是你整个项目的**第一块基石**，报告第一页就该放它。

### 图 5 `fig5_pareto_frontier.png` —— Pareto 前沿（报告的核心图）

- 横轴尾部出字延迟（CVaR90），纵轴单位成本，两者都是**越小越好**。
- **该看到的**：绝大多数点落在右上（被支配），只有沿着左下边界的一条线上的配置值得选。
- 如果已经跑过 `tc_eval.py`（质量表存在），图里会用**空心灰圈**标出"质量不达标被剪枝"的配置，
  前沿只在满足质量底线的点里计算——**这张图同时展示了"质量约束如何改变选择"**。
- 这张图回答："**在满足质量和延迟的前提下，我到底有几个真正值得选的方案**"。

> 脚本会顺手打印"前沿上有几个配置、被支配几个、被质量剪掉几个"。
> 报告图注建议：**"在满足质量底线的 __ 个配置中，仅 __ 个位于 Pareto 前沿；其余均被支配。"**

## 三、用两种独立方法估带宽（交叉验证）

### 方法 A：图 3 的过原点拟合

`tc_analyze.py` 会自动打印：`由图 3 过原点拟合得到的有效带宽 ≈ ___ GB/s`

### 方法 B：用单个模型手算

```powershell
& "D:\llm\venv\Scripts\python.exe" tc_bandwidth.py
```

它会用"权重 GB ÷ TPOT 秒"逐个模型算一遍。

**判断标准**：

| 情况 | 说明 |
|---|---|
| 两个方法差 < 15%，各模型之间也接近 | ✅ 访存受限确认，可以进 S5 |
| 某个模型明显偏离 | 看它是不是被 CPU offload 了（日志里出现 CPU buffer）；或那一格刚好降频 |
| 全部偏低（比如只有 60 GB/s） | 检查是否 `-ngl 99` 生效；是否插电 |

**参考量级**：RTX 4060 Laptop 标称带宽约 256 GB/s。本项目已实测：3B-Q4 反推 217 GB/s、7B-Q4 反推 241 GB/s，即 **200–245 GB/s（标称的 78%–96%）**。
如果你测出来落在这个区间，说明数据和机器都对；低于 150 就要查是否被 CPU offload 或降频。
如果你测出来在这个区间，恭喜，数字是对的。

## 四、三个结论（模板，填上你的数字）

这三个结论就是你报告的核心。**每个都要"现象 + 数字 + 解释"三件套。**

**结论 1：decode 阶段是访存受限，不是算力受限。**
> 证据：三个不同大小的模型（1.12 / 2.10 / 4.68 GB）在并发 1 下 TPOT 分别为 ___ / ___ / ___ ms，
> 与权重字节数近似成正比（图 3 过原点，R² ≈ ___）。反推有效带宽 __ GB/s，
> 与 4060 标称 256–272 GB/s 的比值为 ___%，差值来自 kernel 效率与读写混合。

**结论 2：批处理能大幅摊薄成本，但有上限。**
> 证据：并发从 1 到 32，单位成本由 ___ 降到 ___（降为 1/__），
> 而单请求 TPOT 只变化 ___%。到并发 32 时曲线已明显趋平，边际收益接近于零（图 2）。

**结论 3：显存是这个尺寸显卡上真正的约束，它把设计空间剪成了非矩形。**
> 证据：60 个组合里 ___ 个因 KV cache 超出 8 GB 而无法运行，
> 且被剪掉的格集中在"大模型 × 长上下文 × 高并发"这一角（表 3 / `tc_env_check.py` 第 5 节）。
> 例如 7B-Q4 在 8192 上下文下最多只能开到并发 ___。

> **写报告时注意**：结论里不要出现"我觉得""大概"。每个数字都要能追到 `summary.csv` 的某一行。

## 五、数据异常排查清单

| 症状 | 先查什么 | 处理 |
|---|---|---|
| 某格 TPOT 明显高于同模型其他格 | `clock_sm_median` 是否偏低 | 降频。单独重跑该格（`--only`），避开热的时候 |
| `n_repeats` 不是 3 | 该格中途失败过 | 删掉该格数据行后重跑 |
| TTFT 小得不合理（< 10 ms） | 是否 prompt cache 命中 | 检查是否每个请求都有随机 nonce |
| 吞吐在高并发反而下降 | 显存压力 / 调度开销 | 这是真实现象，**保留并解释**，别删 |
| 某个模型的带宽与其他模型差 2 倍 | 是否部分层跑了 CPU | 看日志 `CUDA0 model buffer size` 与 `CPU model buffer size` |

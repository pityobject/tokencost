## 一、模型长什么样（先看结论，再看推导）

```
decode（每出一个 token 的时间）：

    TPOT = max(  (权重字节 + KV字节×上下文×并发) / 有效带宽 ,
                 2×参数量×并发 / 有效算力  )  + 服务开销 c_srv × 并发

prefill（首字之前的那段时间）：

    TTFT = max(  权重字节 / 有效带宽 ,
                 2×参数量×提示长度×min(并发, B_SAT) / 有效算力  )
             + 服务开销 c_srv × 并发  +  首字固定开销 ovh_ttft

吞吐与成本（必须算上 prefill，否则高估吞吐 15–30%）：

    每条请求占用槽位的时间 = TTFT + 生成长度 × TPOT
    吞吐 = 并发数 × 生成长度 / 该时间
    成本 = 1e6 / 吞吐
```

> **【2026-10-31 实测修正 · 务必读】**
> 最初的 3 参数版本（末尾是 `+固定开销`、且 KV 不乘并发）在真实数据上
> **成本 MAPE 33.5%、最大误差 71.5%**，残差是系统性的：并发 1 高估 1.7 倍、并发 32 低估到 0.39 倍。
> 数据里同时摆着线索：**GPU 利用率从 89% 掉到 48%、功耗从 79 W 掉到 49 W**——显卡在空转。
> 用 `llama-batched-bench` 绕开 HTTP 测纯后端：并发 32 时后端能跑 2377 t/s，server 只有 940（**40%**）。
> 补上 `c_srv·并发`（每条流每步的采样/序列化/推流开销）与 `min(并发, B_SAT)`（prefill 并行饱和）后：
> **成本 MAPE 8.70%、最大误差 24.2%**（墙钟口径 11.28% / 35.1%）。
> 完整过程见 `审计记录_十五轮对抗性复核.md` 第五轮。

**整个项目只有 6 个待定参数**（每个都有物理含义，不是凑出来的）：

| 参数 | 单位 | 物理意义 | 你要能回答的追问 |
|---|---|---|---|
| 有效带宽 `BW` | GB/s | 每秒能从显存读出多少字节 | "为什么不是标称的 272？"→ kernel 效率、读写混合、地址不连续 |
| decode 算力 `PEAK_dec` | TFLOP/s | decode 步（瘦长矩阵乘）的有效算力 | "为什么和 prefill 分开？"→ 两者 kernel 效率差 2.4 倍，合成一个时最大误差 19.5% |

## 二、推导（请自己动手写一遍，面试要能写）

### 2.1 decode：为什么是"取最大"

生成一个 token，机器必须：

**读**：全部权重（因为每个权重都要参与计算）。字节数 = `W`。
另外，注意力的每一步都要回顾全部上下文，所以还要读 KV cache：字节数 ≈ `kv_per_token × 上下文长度`。

**算**：每个参数要做一次乘法和一次加法 = 2 次浮点运算。所以算力需求 = `2 × P`（P = 参数量）。

```
读的时间 = W / 带宽          算的时间 = 2·P / 算力
实际时间 = max(两者)          ← 谁慢谁是瓶颈
```

这就是 roofline 模型的离散版本。**"取最大"是关键**：瓶颈不可能是"两者都满"，只能是最慢的那个。

### 2.2 批处理（并发 b）：为什么读变便宜、算变贵

同时跑 b 条序列时：
- 权重**只读一次**就给 b 条用 → 每条摊到 `1/b`
- 但算力要算 b 倍 → `2·P·b`

```
TPOT(b) = max( (W + KV) / 带宽 ,  2·P·b / 算力 )  + ovh
```

- b 小的时候：**第一项赢**（读显存慢）→ 加并发不增加单条延迟，白赚吞吐
- b 大的时候：**第二项赢**（算力满）→ 加并发让每条都变慢

### 2.3 拐点：一个可以直接算出来的数

令两项相等，解出 b：

```
b* = (W + KV) / P × 算力 / (2 × 带宽) = w · PEAK / (2 · BW)      （w = 每位参数占的字节数）
```

**它的意义**：并发超过 b*，**单位成本不再下降**，只是延迟变差。

而成本 = `1e6 · TPOT / b`：
- b < b*：成本 ∝ 1/b（下降）
- b > b*：TPOT ∝ b，成本 ∝ b/b = 常数（**趋平**）

> ⚠️ 注意一个反直觉的点：超过拐点后成本是**趋平**，不是"上升"。
> 如果你一开始以为"会上升"，实测发现是"趋平"，那就是一次真实的假设被修正——**写进报告**（详见 S7 篇）。

### 2.4 TTFT：为什么是算力密集

prefill 要一次性把 L 个 token 全过一遍：算力需求 ≈ `2·P·L`（注意力那一项是 L²，L 小时可忽略），
而权重只读一次（`W/带宽`）。L = 256 时，`2PL/算力` 通常远大于 `W/带宽`，所以 TTFT 主要由算力决定。

**这就是为什么"首字慢"和"出字慢"是两回事，优化手段也完全不同。**
如果你在面试里能把这句话讲清楚，就已经超过大多数候选人了。

## 三、为什么用"对数比的平方"做损失函数

拟合的目标是最小化：

```
Σ [ ln(预测值 / 实测值) ]²
```

三个原因：

1. **相对误差，不是绝对误差。** 一个 5 ms 的模型和一个 25 ms 的模型，我们都希望"错 5%"，而不是"都错 1 ms"。
2. **对称。** 预测偏高 10% 和偏低 10% 惩罚相同（普通比值不对称：1.1 和 0.909 不等距）。
3. **量级无关。** 成本从 200 到 24000 跨两个数量级，直接用差值会让大值主导。

## 四、为什么只用 12 个格标定（而不是全用）

| 做法 | 问题 |
|---|---|
| 用全部 50 格拟合 | 就没有"没见过"的格了，误差一定很好看，但**毫无意义**（自己出题自己打分） |
| 只用 5 格 | 3 个参数 + 每格 2 个观测量，勉强够，但参数估计很不稳 |
| **12 格** | 每个模型组合 2–3 格、每个上下文 4 格、每个并发 3 格，**覆盖了极端值和中心**；同时留出 33 格做检验 |

这就是**实验设计（DOE）**的基本思想：**用尽量少的点，抓住系统的主要变化方向。**

`tc_config.py` 里的 `CALIB_CELLS` 已经按这个原则挑好了，你不需要改。**改动它就等于改了实验设计**，那要在报告里说明理由。

## 六、预测区间是怎么算出来的（这一段能让你脱颖而出）

你给出"成本 400 GPU 秒"其实应该说"成本 400，90% 可能在 380–421 之间"。这个区间由两层误差合成：

```
σ_pred²  =  σ_fit² × n/(n−p)   +   σ_noise² / k
              └─ 第一层：参数不确定性 ─┘  └─ 第二层：测量抖动 ─┘

90% 区间半宽 = t(0.95, df) × σ_pred        df = 2×格数 − 参数个数
```

| 符号 | 含义 | 为什么要这么处理 |
|---|---|---|
| `σ_fit` | 标定集残差的标准差 | 残差小说明模型贴合 |
| `× n/(n−p)` | 自由度校正（n 观测、p 参数） | 用 12 个点估 3 个参数，残差会偏小，必须**放大**才诚实 |
| `σ_noise` | 同一格 3 次重复之间的抖动 | 纯测量噪声，与拟合无关，所以不会自我美化 |
| `÷ k` | 新格也是 k 次重复取中位数 | k 次平均的抖动是单次的 1/√k |
| `t(0.95, df)` | t 分布分位数，不是 1.645 | 小样本（df≈21）时 t 的尾巴更厚，区间必须更宽；用正态就是**不诚实** |

> 面试可能这样问："你的 90% 区间是怎么来的？"
> 答："两层：参数不确定性用残差标准差做自由度校正，测量噪声用格内重复的抖动除以 √3；
> 再用 t 分布而不是正态，因为标定样本只有 12 个格。"
> ——**这一句就能证明你不是调包，而是懂。** 大多数人只会说"我取了个 ±10%"。

## 六点五、模型的两个已知简化（主动写在报告里，别等人问）

**（曾经是简化，现已修正）prefill 项必须乘并发数。**

最初我把 TTFT 写成 `max(W/BW, 2·P·L/PEAK) + ovh`，**不含并发**。第一格实测就打脸了：

| 并发 | TTFT 实测 | 旧公式预测 |
|---|---|---|
| 1 | 76 ms | 68 ms ✓ |
| 4 | **272 ms** | 68 ms ✗（差 4 倍） |

原因很直接：b 条 296-token 提示同时到达时，prefill 的总浮点量是 `2·P·L·b`，不是 `2·P·L`。
加上 `×b` 之后，取 `PEAK≈27 TFLOP/s` 同时对上两点（68/272 vs 实测 76/272）。

**修正后的写法**：`TTFT = max(W/BW, 2·P·L·b/PEAK) + ovh`。

> 但仍留一个限制要写进报告：我们的压测是**同步波次**（b 个请求同时发），
> 所以测到的是"最坏情况"的 TTFT。真实服务里请求是错峰到达的，TTFT 会明显更低。
> 报告里要写清这一点，否则会被问"你线上也这样吗"。

**简化 2：KV 读取按平均上下文长度估算。**
真实系统里批内各序列长度不一，KV 访存是各序列之和。我们用 `提示长度 + 生成长度/2` 当平均值，
在长度分布很偏（比如混了 128 和 8192）时会低估。所以本项目固定了提示长度（256 token），
就是为了让这个简化成立——**这也解释了为什么网格里不扫提示长度**。

> 把这两条写进"局限"一节，是加分项。藏着不说，被问出来就是减分项。

## 七、如果没通过，怎么系统排查（不要改数据！）

**永远先看残差图 `figures/fig4_pred_vs_actual.png` 的右半边**：误差是随哪个维度系统性变化的？

| 残差形态 | 说明缺失了什么 | 怎么改模型 |
|---|---|---|
| 误差随**并发**单调变大 | 缺了"随并发增长的调度开销" | 加一项 `a×b`（多一个参数） |
| 误差随**上下文**变大 | KV 项系数不对（可能开了 flash attention 或 KV 量化） | 给 KV 项加一个可拟合系数 |
| 某个**模型**整体偏移 | 该模型可能被 CPU offload，或层数/头数差异 | 查日志的 `CPU model buffer size`；或给该模型加偏置 |
| 误差**全部同向**（都偏高或都偏低） | 固定开销项不准，或用了错误的权重字节数 | 核对 `weight_bytes` 与实际文件大小 |
| 误差在**高并发 + 长上下文**集群出现 | 显存压力导致抢占/换页 | 在模型里加"显存压力"项，或明确声明适用域 |

**改完之后，仍然只用那 12 个点重新拟合，然后用同一批留出格重新验证。**
这正是科学方法：**模型可以有第二版，但检验集不能换。**

### 如果加了参数还是过不去，怎么办

那也有价值。诚实的写法是：

> "本模型在并发 ≤ 16 的范围内 MAPE 为 4.2%，但在并发 32 时系统性高估 11%。
> 残差分析显示高并发区存在未被建模的机制（推测为 KV cache 内存压力与调度开销）。
> 我们把模型的**适用域**明确限定为并发 ≤ 16，并在推荐器中标注这一限制。"

**限定适用域 + 说清原因，是完全合格的工程结论。** 比硬凑一个数字诚实得多，评委也更认可。

## 八、三个必须能回答的问题

1. **"你怎么保证不是过拟合？"**
   → 12 个点拟合 3 个参数，参数/数据比 1:4；且检验全部在 68 个未参与拟合的格上完成。

2. **"换个显卡，你的模型还能用吗？"**
   → 能，但只需要重测**两个数**（带宽、算力）。模型的**结构**（读权重 + 算力上限 + 取最大）
   是与硬件无关的物理规律。这就是为什么它比一张 benchmark 表格值钱。

3. **"你这三个参数是不是拍出来的？"**
   → 不是。初始值只用来启动优化器（200 GB/s / 15 TFLOP/s），
   最终值由最小化对数残差确定；而且拟合结果与"用 S4 的方法独立估出的带宽"吻合。

## 一、指标定义表（写报告时直接用）

| 指标 | 定义 | 反映什么 | 怎么算 |
|---|---|---|---|
| **TTFT** 首字延迟 | 发请求 → 第一个内容 token 到达 | prefill 速度 + 排队 | `t_first - t_send` |
| **TPOT** 出字间隔 | 第一个 token 之后，**平均每个** token 的间隔 | decode 速度（带宽） | `(t_last - t_first) / (n_out - 1)` |
| **总耗时** | 发请求 → 最后一个 token | 用户体验 | `t_last - t_send` |
| **吞吐** | 整机每秒产出多少 token | 批处理效率 | `token 总数 / 墙钟时间` |
| **单位成本** | 每百万 token 占多少 GPU 秒 | **项目的目标函数** | `1e6 / 吞吐` |
| **CVaR90** | 最差 10% 请求的平均延迟 | 尾部风险 | 排序后取最差 10% 求均值 |
| **P90** | 90% 的请求快于这个值 | 尾部风险（粗） | 分位数 |

### 为什么成本用"GPU 秒/百万 token"而不是"tokens/s"

因为 `tokens/s` 不可比：机器不同、并发不同、上下文不同，这个数会飘。
而"生成 100 万个 token 要占用多少 GPU 秒"是**硬件无关**的账，可以直接换算成钱：

```
成本($) = (GPU秒 / 1e6) × (显卡小时单价 / 3600)
```

报告里给两个版本：主指标用 GPU 秒（诚实、可复现），附一张按公开算力单价折算的 $/百万 token（并标注"仅供量级参考，单价是假设"）。

### 为什么主风险指标用 CVaR90 而不是 P99

这是你项目里第一个"有统计含量"的决定，面试很可能追问：

1. **样本量**：我们每格只发 16–64 个请求。要可靠估计 P99，至少要几百个样本。用 24 个样本算 P99，算出来的其实接近"最大值"。
2. **可优化性**：P99 是分位数，不可导、不可用梯度方法优化；CVaR 是"最差 10% 的均值"，**可优化、且是凸的**。后面做配置选择时要用它。
3. 两者方向一致，CVaR90 可以理解成"尾部延迟的平均水平"。

> 报告里写这句：**"我们用 CVaR90 代替 P99 作为尾部风险度量，原因一是样本量不足以可靠估计 P99，原因二是 CVaR 可优化。"** —— 这一句就能把"随便跑跑"和"懂统计"区分开。

### 吞吐到底怎么算（这一行算错，全项目的目标值都错）

代码里现在用的是**唯一正确的算法**：

```
吞吐 = 整轮实验生成的总 token 数 ÷ 整轮实际墙钟时间
     = Σ n_out ÷ (最晚结束时刻 − 最早开始时刻)
```

**不要**写成 `每请求速率 × 并发数`。为什么不行：请求会排队，每个请求的"耗时"里已经包含了排队等待，
再乘并发数等于把等待重复计了一次——高并发下会系统性**低估**吞吐，也就是**高估**成本，
而成本正是本项目的目标值。代码里为此专门给每个请求记了 `t_start_rel / t_end_rel` 两个时间戳。

### 还有一个隐形瓶颈：你的 Python 脚本自己

用 32 路并发压测时，客户端也在做大量工作：32 条流式连接、每个 chunk 一次 JSON 解析。
单核跑满时，你测到的就不再是"显卡能跑多快"，而是"我的脚本能跑多快"。

所以 `tc_run_cell.py` 会记录 **`client_cpu_pct`**（本进程占单个核的百分比）：

| `client_cpu_pct` | 含义 | 怎么办 |
|---|---|---|
| < 70% | 客户端不是瓶颈 | 放心用 |
| 70–90% | 接近饱和，吞吐可能被压 | 报告里标注；或把并发分成两个进程跑 |
| > 90% | **客户端已成瓶颈** | 该格吞吐只能当"下限"报告，不能当模型上限 |

> 这个数字会随每格一起落盘。**报告里如果某一格 `client_cpu_pct` > 90%，必须写明**——
> 这比事后被面试官问出来要体面得多。

## 二、读代码：`tc_loadgen.py` 关键 30 行

你只需要理解三件事，其余当成黑盒也能用。

### 2.1 为什么用 `async`（异步）

```python
async def one_request(...):
    ...
await asyncio.gather(*(worker(i) for i in range(n_requests)))
```

普通 Python 是"一件一件做"：发第 1 个请求 → 等它全生成完 → 再发第 2 个。
压测需要的是"同时发 N 个请求"，所以用 `async`：发出去之后**不干等**，去发下一个，谁的回复来了就处理谁。

> 类比：一个人点菜（同步）vs 服务员同时照看 8 桌（异步）。

### 2.2 什么是"流式返回"

```python
async for line in resp.aiter_lines():
    if not line.startswith("data:"):
        continue
```

模型生成不是最后一次性给你全文，而是**一个 token 一个 `data:` 行**推过来（就像打字机）。
所以我们要在每行到达时打一个时间戳 —— 这就是 TTFT 和 TPOT 的唯一数据来源。

**如果不用流式**（`"stream": False`），你只能拿到总耗时，TTFT 和 TPOT 就永远测不出来。这是为什么这一节必须用流式。

### 2.3 三个必须理解的细节

| 细节 | 代码 | 不这么做会怎样 |
|---|---|---|
| 首块不算首字 | `if delta.get("content")` | 服务端先发一个只有 `role` 的空块。把它算成首字，TTFT 会凭空少几十毫秒 |
| 每个请求加随机后缀 | `make_prompt(..., nonce=i)` | llama-server 有 **prompt 缓存**：相同 prompt 再来一次，prefill 时间≈0，你的 TTFT 数据全废 |
| 明确关缓存 | `"cache_prompt": False` | 同上，双保险 |

> **这三条是压测新手最常踩的坑**，也是面试官测试你"是真跑过还是抄的"最常用的问题。
> 报告里写一句"为避免 prompt cache 影响 TTFT，我们对每个请求注入随机非重复前缀并显式关闭 cache_prompt"，专业度立刻不一样。

## 三、测量纪律（6 条，写进报告的方法学一节）

笔记本 + 移动端 GPU 的测量比服务器娇气得多。这六条缺一条，数据就会被人挑刺。

| # | 纪律 | 怎么做 | 为什么 |
|---|---|---|---|
| 1 | **插电 + 高性能电源模式 + 风扇全力** | Windows 设置 → 系统 → 电源 → 最佳性能 | 电池供电会限制 GPU 功耗，速度掉 20%+ |
| 2 | **每次启动后预热** | 代码里已做（`warmup=2`，丢弃结果） | 首次推理要编译 kernel、预热缓存，慢到没有参考价值 |
| 3 | **每格 3 轮重复，取中位数** | `REPEATS = 3` | 报"最好那次"是学术不端，报中位数是工程习惯 |
| 4 | **记录温度与频率** | `tc_gpu.py` 每 2 秒采样一次 | 笔记本会热降频。不记录，你无法解释"为什么第 20 格突然变慢了" |
| 5 | **所有格在同一次开机会话内跑完** | 一次跑 3 小时，别分 5 天 | 系统更新、驱动更新、后台程序变化都会污染数据 |
| 6 | **固定生成长度（128 token）** | `GEN_TOKENS = 128`；请求体带 `"ignore_eos": true` 强制生成满 | 长度不固定，TPOT 没法比；且太短时固定开销占比过大 |

## 四、跑一次单格实验

**目标**：跑通"启动服务 → 预热 → 3 轮测量 → 落盘 → 关服务"的完整流程。

```powershell
cd C:\Users\王钟垚\Desktop\find_career\tokencost\code
& "D:\llm\venv\Scripts\python.exe" tc_run_cell.py 3B q4_k_m 2048 4 --repeats 1
```

**预期输出**（下面是这台机器上实测的真实样子）：

```
=== 单格实验：3B q4_k_m ctx=2048 并发=4 ===
    服务就绪 4.3s  日志 server_3B_q4_k_m_ctx2048_c4.log
    第1/1轮  TTFT   262.8ms  TPOT   12.4ms  吞吐   278.4 tok/s  客户端CPU 10%
结果：
  ...
```

**两个数字看起来"反直觉"，但都是对的**，下面有专门解释：TTFT 262 ms（单并发只要 76 ms）、
吞吐 278 tok/s（而 `99.3 × 4` 应该是 397）。

### 怎么判断这次数据是"可信的"

对照检查五项，全过才算数（"期望"列是这台机器 3B-Q4 / ctx2048 / 并发4 的实测值）：

| 检查 | 期望（实测基准） | 不对说明什么 |
|---|---|---|
| `n_ok` | **24** | 有请求失败，看 `n_fail` 和日志 |
| `n_out_median` | **128**（精确等于） | `ignore_eos` 没生效（某些版本字段名不同），TPOT 仍可用但要记录真实长度 |
| `prompt_tokens_median` | **约 297** | 提示词实际 token 数 ≠ 配置里写的 256，属正常；**以实测为准**，不要用 256 去算 |
| `tpot_p50_ms` | **12–13 ms**（并发4）<br>**9–10 ms**（并发1） | 若差 2 倍，多半没上 GPU（看日志 `CUDA0 model buffer size`） |
| `ttft_p50_ms` | **260–275 ms**（并发4）<br>**75–80 ms**（并发1） | 若并发4 时仍只有 76 ms，说明 TTFT 没受 prefill 竞争影响——检查 `--parallel` 是否生效 |
| `client_cpu_pct` | **< 70%** | > 90% 时该格吞吐只能当下限报告 |

> **为什么 TTFT 会随并发涨**：b 条 296-token 提示同时到达，prefill 的浮点量是 `2·P·L·b`，
> 不是 `2·P·L`。实测：并发1 → 76 ms、并发4 → 263 ms，正好接近 4 倍。
> 这是物理现象，**不是 bug**，而且已经写进 S5 的公式（prefill 项乘 `b`）。
>
> **为什么 `n_out` 现在必须精确等于 128**：请求体里带了 `"ignore_eos": true`
> （见 `tc_loadgen.py`），强制生成满 `max_tokens`。这样每格的生成长度一致，
> TPOT 才能横向比较。**如果它不等于 128，说明这个 build 不认这个字段**，要回来改代码。

### 为什么实测吞吐远低于"单请求速率 × 并发数"

这是 S2 最容易让人怀疑"是不是测错了"的地方。以实测为例：

| 步骤 | 吞吐 | 损失 | 原因 |
|---|---|---|---|
| 天真算法 `99.3 × 4` | 397 | — | ❌ 错。它假设 TPOT 不变、且 prefill 免费 |
| 扣除批处理效率（TPOT 10.07→12.4） | 323 | −19% | 请求完成时间错开、槽位重填、批内长度不齐 |
| 再扣除 prefill 占用 | **277** | −14% | 每条请求占槽位的时间是 `TTFT + 128×TPOT` |
| 实测 | **278.4** | — | ✅ 与第三步吻合 |

**关键公式**（已写进 S5 与代码）：

```
每条请求占用槽位的时间 = TTFT + 生成长度 × TPOT
吞吐 = 并发数 × 生成长度 ÷ 该时间
```

如果只拿 `并发 ÷ TPOT` 算吞吐，会**高估 16%**（并发4 时），而成本 = `1e6/吞吐`，
于是成本会被系统性低估——**目标值错了，整个项目的结论都会偏**。

> 顺带一句：这也是为什么"吞吐"这个词在真实服务里必须写清口径。
> 我们用的是 **端到端墙钟吞吐**（含 prefill、含排队），这是做成本核算时唯一有意义的口径。

## 五、卡住了怎么办

| 现象 | 原因 | 解决 |
|---|---|---|
| 端口被占用 | 上次的 llama-server 没关干净 | `Get-Process llama-server \| Stop-Process -Force` |
| `等待服务就绪超时` | 模型太大 / 显存不足 / 磁盘慢 | 看 `logs/server_*.log` 最后 20 行；换小模型或更小 ctx |
| 全部请求失败 | 服务起来了但 API 路径不对 | 确认 `{BASE_URL}/v1/chat/completions`；浏览器打开 `http://127.0.0.1:8090` 能进 web UI |
| TTFT 异常小（< 10 ms） | prompt cache 命中了 | 检查 `make_prompt` 的随机后缀是否生效 |
| TPOT 波动很大 | 后台程序抢资源 / 降频 | 关掉浏览器标签、录屏、杀毒扫描；插电 |

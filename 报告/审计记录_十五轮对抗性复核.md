## 一、致命问题：`--ctx-size` 与 `--parallel` 的语义搞错了

### 事实

`llama-server` 的 `--ctx-size`（`-c`）是**整个服务端的总上下文**，服务端会把它**按 `--parallel` 平分给各槽位**。
这是 llama.cpp 社区里反复出现的话题——per-slot context 后来被单独做成参数（[PR #23340 `--slot-context`](https://github.com/ggml-org/llama.cpp/pull/23340)），
统一 KV 下的槽位限制也被专门修过（[PR #23694](https://github.com/ggml-org/llama.cpp/pull/23694)、[讨论 #27916](https://github.com/ggml-org/llama.cpp/discussions/27916)），
说明"槽位拿到多少上下文"确实是一个**需要显式处理的维度**，不是天然等于你传的那个数。

### 原来的代码错在哪

```python
"--ctx-size", str(ctx),        # ← 错：把"每槽位"当成了"总上下文"
"--parallel", str(conc),
```

后果（以 3B-Q4、ctx=512、并发 32 为例）：总上下文 512，分给 32 个槽位 → **每槽位只有 16 个 token**。
而我们的提示词就有 256 token + 生成 128 token。**所有请求都会被截断**，测出来的 TTFT/TPOT 全是废数据。
更糟的是它不会报错，只会在响应里带 `truncated: true` —— 你不查就发现不了。

### 连带发现的第二类约束（我原来没算）

要让每槽位有 `ctx` 个 token，必须传 `ctx × 并发`。但模型原生最大上下文是 **32768**（Qwen2.5），
超过就得开 YaRN（会改变模型行为，本项目不做）。于是多出一条硬约束：

```
ctx × 并发 ≤ 32768
```

它剪掉的不是"显存不够"的格，而是"上下文装不下"的格：

| 被剪掉 | 原因 |
|---|---|
| 2048 × 32 = 65536 | 超 32768 |
| 8192 × 16 = 131072 | 超 32768 |
| 8192 × 32 = 262144 | 超 32768 |

**因此设计空间从"60 格、约 52 可行"改为"60 格、45 可行"**（7 格仅因上下文超限，8 格同时超上下文与显存）。
12 个标定格中有一个（3B-Q8 / 2048 / 32）因此不可行，已替换为（3B-Q8 / 8192 / 4）。

### 已经做的修正

| 文件 | 改了什么 |
|---|---|
| `code/tc_config.py` | 新增 `N_CTX_TRAIN=32768`、`total_ctx()`、`ctx_cap_ok()`；`infeasible_reason()` 改为返回**全部**违反的约束 |
| `code/tc_server.py` | `--ctx-size` 改为 `cfg.total_ctx(ctx, conc)`，并写了醒目注释 |
| `code/tc_probe.py` | **新增**：用服务端自己回报的 `tokens_evaluated / truncated / tokens_cached` 实测每槽位上下文 |
| 手册 04（S3） | 新增"开跑前必做"的探针步骤 + 该细节的专门段落 |
| 计划 v2 / 手册 00/05/06/08 / README / 报告模板 | 全部数字改为 45 可行 / 12 标定 / 33 留出 |

### 为什么不是"相信我就好"

`tc_probe.py` 的设计原则是**不依赖任何文档**：发一条接近 `ctx` 长度的提示，让服务端告诉你它实际评估了多少 token、
有没有截断。跑通它，这条语义就被钉死了；跑不通，说明还有别的问题，会在 S3 之前暴露，而不是在 45 格数据跑完之后。

## 二、方法学问题 1：参数可辨识性没交代

三个参数里，`PEAK`（有效算力）只在**算力受限区**才被数据约束。而 decode 在并发 ≤ 32 时很可能**全程访存受限**
（拐点 `b* = w·PEAK/(2·BW)`，按拟合值算 7B 约 25、3B 约 28、1.5B 约 40+）。
如果标定集的格全部落在访存受限区，`PEAK` 就基本只由 TTFT 那几条观测定出来，**拐点是外推，不是实测**。

**修正**：`tc_model.py` 新增可辨识性诊断，直接打印"标定集中有几个格处于算力受限区"；
为 0 或 <3 时会明确警告，并要求报告写"拐点未经直接验证"。假数据自检时确实报了 1/12，警告生效。

---

## 三、方法学问题 2：质量评测的样本量撑不起结论

60 道题时，单个准确率的 95% 置信区间半宽约 **±12 个百分点**。
"3B-Q4 91.7% vs 3B-Q8 95%"这种差距，**完全可能只是这 6 道题恰好蒙对/蒙错**。
如果拿它去写"Q8 比 Q4 质量更好"，是过度解读。

**修正**：`tc_eval.py` 增加 Wilson 区间（小样本比正态近似稳），逐行打印 `95%CI`，
并明确要求：差距小于噪声宽度时，只能写"在这 60 题上没测出差异"，不能写"A 比 B 好"。
想缩窄就 `--n-per-kind 20~30`（题目生成是程序化的，加题零成本）。

## 四、方法学问题 3：验收标准与科研诚信冲突

原文把"MAPE ≤ 8%"写成**验收否决线**。这会诱导一条危险的路：数字不达标 → 反复调参 → 不知不觉在挑数据。

**修正**：改为**目标值**。项目真正的通过标准是三条：

1. 报出**真实**的 MAPE / 最大误差 / 覆盖率；
2. 做**残差分析**（误差随哪个维度增大），并据此**限定适用域**；
3. 若未达目标，写清"哪一段失效、推测原因、如何验证"。

代码里的提示也从"验收判定"改为"目标达成情况"，并加了一行：**为了达标去改数据，项目立刻归零**。

**可以按这个做。** 理由不是"我觉得没问题"，而是：

真实数据里会有我没建模的东西（HTTP/序列化开销、批内长度差异、热降频、KV 碎片）。
我的判断是"大概率落在 5%–15%"，达标的希望不小但不保证。**这恰恰是项目值得做的原因**——
一个必然达标的指标，不值得做；一个你事先不知道答案、且有明确判据的问题，才值得做。

# 第二轮复核（查"目标变量本身可不可信"）

第一轮查的是"能不能跑通"，这一轮查的是"**跑出来的数是不是这个项目要的那个数**"。又发现 3 处要改。

## 六、吞吐算法有系统偏差（已修，且这是目标变量的分母）

### 问题

原来的汇总用 `每请求速率 × 并发数` 近似吞吐：

```python
per_slot_tps = mean(n_out / total_s)
throughput   = per_slot_tps * min(concurrency, len(ok))
```

每个请求的 `total_s` 里**已经包含排队等待**（从发出到最后一 token 的全过程）。
再乘并发数，等于把排队时间重复计了一次 → 高并发下**低估吞吐** → **高估成本**。
而成本 `1e6/吞吐` 正是整个项目的目标变量。

### 修正

给每个请求加记 `t_start_rel / t_end_rel`，汇总时用**整轮墙钟**：

```
吞吐 = Σ n_out ÷ (最晚结束 − 最早开始)
```

### 验证（假服务端每 token 固定 20 ms，理论值 = 并发 × 50 tok/s）

| 并发 | 理论吞吐 | 修正后实测 | 旧算法 |
|---|---|---|---|
| 1 | 50 tok/s | **44.8** | 44.8 |
| 4 | 200 tok/s | **184.3** | 184.0 |
| 16 | 800 tok/s | **696.7** | 697.0 |

低并发下两法一致（没有排队），高并发下新算法随墙钟一起计入波次切换与排队，
可比性更强；差异不大，但**定义对了**——这决定了"成本"这个数在报告里站不站得住。

## 七、隐形瓶颈：压测脚本自己可能成为天花板

32 路并发时，客户端要维护 32 条流式连接、每 chunk 解析一次 JSON。单核跑满时，
测到的不是"显卡多快"，而是"我的 Python 脚本多快"。

**修正**：`tc_run_cell.py` 记录 `client_cpu_pct`（本进程占单核百分比），超 90% 时当场打印警告；
手册 S2 给了三级判读表，并要求报告里标注"该格吞吐只能当下限"。

## 八、模型有两处结构性简化，必须写进局限

| 简化 | 影响 | 处置 |
|---|---|---|
| TTFT 公式不含并发 `b` | prefill 与 decode 抢算力、分块预填充 → 高并发下**低估 TTFT** | 残差若随并发变大即为此因；可加 `a·b` 项，或明确写"高并发下 TTFT 为乐观估计" |
| KV 读取用"提示+生成/2"当平均上下文 | 批内长度分布偏斜时低估访存 | 本项目固定提示长度 256 token，正是为了让该简化成立；这也解释了**网格为何不扫提示长度** |

已写进 `手册/06` 新增的"六点五、模型的两个已知简化"。

## 九、其他：单位与工程完整性

| 项 | 处理 |
|---|---|
| GB vs GiB 混用 | 显卡标称 8188 MiB ≈ 8.59×10⁹ B；统一按十进制 GB 估计并留 ~1 GB 余量（阈值 7.6 GB），`tc_env_check.py` 末尾已注明 |
| 缺依赖清单 | 新增 `code/requirements.txt`（含"一键装"注释） |

# 第三轮复核（查"结论会不会在物理上说不通"）

前两轮查"能不能跑""数对不对"，这一轮只问一句：**推荐出来的东西，物理上做得到吗？**

## 十、逻辑错误：推荐器会推荐"装不下请求"的配置（已修）

`tc_recommend.py` 原来只检查显存、SLA、质量，**没有检查每槽位上下文能否装下工作负载的提示长度**。
后果很具体：用「长文档摘要」场景（平均提示 2048 token）跑推荐器，它会推荐 `ctx=512` 的配置——
一个连提示词都塞不进去的配置。这个错误不会让程序报错，只会让结论变得荒谬。

**修正**：加入"上下文可容纳"约束，按提示长度的 **95 分位 + 生成长度** 计算需求。

**修正前后对比**（假数据自检）：

| 场景 | 修正前 | 修正后 |
|---|---|---|
| 长文档（提示 2048） | 会推 `ctx=512` 的格 | **35 格被剪**，只在 `ctx=8192` 里选 |

出局原因分布现在有四类：显存 15 格 / 上下文装不下请求 35 格 / 质量 0 格 / SLA 6 格。
**这张"四类剪枝表"本身就是报告里"约束剪枝"最有说服力的一张表。**

## 十一、用实测值而不是名义值（已修）

模型里的提示长度原来固定写 `cfg.PROMPT_TOKENS = 256`。但实际提示的 token 数由 tokenizer 决定，
通常会差 5–10%。而 TTFT 的 prefill 项 ≈ `2·P·L/PEAK`，与 L 成正比——**差 8% 就白送 8% 误差**。

**修正**：改用每格实测记录的 `prompt_tokens_median`。这条不改变结论方向，只是让误差少一点。

## 十二、探针的边界太紧（已修）

`tc_probe.py` 原来发 `0.9×ctx` 的提示、要求评估到的 token ≥ `0.8×ctx`。
但"字符→token"是近似换算，如果实际 token 比估计多 10%，服务端就会真的截断，
探针会**误报"上下文不足"**，然后你去改一个本来没问题的参数。

**修正**：提示降到 `0.7×ctx`，判定阈值放到 `0.5×ctx`。让探针只回答"大致够不够"，
不承担"精确测量"的职责——精确测量是正式实验的事。

## 十三、质量表缺项会被静默剔除（已修）

Pareto 图里"质量不达标"是用 `acc < best-3pp` 判定的。如果质量表里根本没有某个组合
（比如只跑了 `tc_eval --only 3B`），`acc` 是 NaN，比较结果为 False → 该组合被**当成质量不达标悄悄踢掉**。

**修正**：NaN 视为"无法判断"，**保留**并参与前沿计算，而不是默认淘汰。

# 回答"中途出错会不会毁掉含金量"

这是设计时就考虑过的问题。结论：**技术性错误几乎都能局部修复，真正会毁掉项目的只有四件事，
而它们都不是技术问题，是诚信问题。**

## 一、错误的影响半径表

| 你会犯的错 | 影响半径 | 修复成本 | 会不会影响结论 |
|---|---|---|---|
| 环境装错 / 缺 DLL | 0 格 | 30 分钟 | 不影响 |
| 某一格跑失败（OOM） | 1 格 | 重跑该格 | 不影响，**失败本身就是证据** |
| 某格数据明显异常（降频） | 1 格 | `--only` 重跑该格 | 不影响（中位数会缓解） |
| 跑完发现忘了预热 / 忘了关 cache_prompt | 全部 | 全部重跑（2–3 h） | 不影响，只是多花机器时间 |
| 模型 MAPE 只有 15% | 结论强度 | 改模型 1–6 小时 | 不影响，**如实报告 + 限定适用域即可** |
| 覆盖率不在 82–96% | 结论强度 | 改区间估计方法 | 不影响，这本来就是常见结论 |
| 手改了 raw_cells.jsonl | **全部** | 不可修复 | **会毁掉项目** |
| 看过留出集结果后又改标定集 | **全部** | 不可修复 | **会毁掉项目** |
| 隐瞒跑不动的格 | 局部→全局 | 不可修复 | **会毁掉项目** |
| 把 `_selftest/` 的假数据当成结果 | 全部 | 可修（重跑） | 会，但能查出来 |

## 二、四道结构性保护

1. **标定/留出是预先写死在 `tc_config.py` 里的**（12 格固定、33 格留出），不是跑完再挑。
   这让你"没法事后作弊"，也让结论不依赖"你执行得完美"——只要不改这两个清单，误差数字就是可信的。
2. **数据是可加、可续跑、逐格落盘的**。任何一格出错，`tc_run_grid.py` 会自动跳过已完成格，只补跑缺的。
3. **分析是数据的纯函数**。模型改了，重跑 `tc_analyze → tc_model → tc_verify` 只要 30 秒，不用重做实验。
4. **失败被当成内容而不是事故**。"15 格被显存/上下文剪掉"是报告的结论之一（可行域非矩形），
   所以"跑不动"从来不等于"白做"。

## 三、唯一不可逆的东西

**不是代码，是数据。** 所以手册里反复强调两条：
① `raw_cells.jsonl` 只增不改，跑完立刻备份到第二个地方；
② 发现问题就重跑那一格，**永远不要手改数字**。

一个手改过的数字，会让你之后所有"这结论对吗"的判断失去依据——那才是真正毁掉含金量的东西，
而不是某一段代码写错。

# 第五轮：真实数据推翻了模型（最大的一次修正）

前四轮都是我这边推演。这一轮是**45 格真实数据把我的模型打穿了**，记录完整过程。

## 二十、3 参数模型在真实数据上失效

# 第六轮：质量基准的三个 bug（评测本身错了两遍）

这一轮不是模型错，是**我的评测方法错**。记录下来，因为它比模型本身更能说明"什么叫对账"。

## 二十五、Bug 1：中文提示词的歧义，把评测结果完全带偏

原提示词：「计算 723 + 450，**只输出最后的数字**，不要任何解释。」
大模型把它理解成「只输出**最后一位**数字」→ 1173 输出 `3`。

后果：7B 在加法上 0%、1.5B 反而 100%，得出"模型越大越差"的荒谬结论。

**怎么发现的**：不是看分数，而是把原始回答摊开看——`expected=1173, answer='3'`，
然后做了三个对照实验：

| 提示 | 7B 回答 |
|---|---|
| 中文原提示 | `3` |
| `What is 723+450? Just the number.` | `1173` ✅ |
| `723 加 450 等于多少？` | `723 + 450 = 1173` ✅ |

模型完全正常，是我的提示词有歧义。改写成「只输出一个阿拉伯数字」后恢复正常。

**教训**：中文里"最后/最近/上面"这类词在有歧义时会被模型严格按字面执行。
评测集的提示词必须做**消歧验证**（同一题用两种表述问，答案应一致）。

## 二十六、Bug 2：百分点与比例混用

判定"某组合是否显著差于最好"时写成：

```python
drop = (best_acc - acc) * 100       # 百分点，例如 5.0
flag = "" if drop < WILSON_NOISE    # WILSON_NOISE = 0.12（比例）
```

5.0 < 0.12 为假 → 5 个百分点的差距被标成"超出统计噪声"。

**修正**：改成比较两个准确率的 95% 置信区间是否重叠。这比固定阈值更稳，也更容易解释。

## 二十七、Bug 3：质量底线定得比测量噪声还紧

140 题下置信区间半宽 ±6 个百分点，而我把质量底线设成"不比最好低 3 个百分点"。
结果 45 个可行配置里**只剩 7B 的 1 格**可选——推荐器直接退化成"永远选最贵那个"。

**修正**：默认底线改为 **6pp ≈ 一个 CI 半宽**，并在代码注释里写清理由。

> 这一条有普适性：**任何"阈值型"决策，阈值都不该小于测量该量的噪声。**
> 否则你是在噪声上做决策，而且看起来还挺严谨。

## 二十八、附带修的一个建模缺口

`simulate()` 对请求长度做对数正态抽样时，**没有按槽位上下文截断**。
长尾里出现超过 8192 token 的"不可能请求"，把尾部延迟抬高，导致长文档场景被判成"无可行配置"。
修正：抽样后 `L = min(L, ctx - GEN)`。

修正后该场景仍然不可行，但原因变得可解释：
**最接近的配置预测 TTFT 1576 ms，超过 1500 ms 预算**——这是物理约束，不是程序失败。

## 二十九、这一轮的净收益

| 项 | 修正前 | 修正后 |
|---|---|---|
| 质量准确率排序 | 1.5B 56.7% > 3B 40% > 7B 38.3%（违背常识） | 7B 81.4% > 3B 77% > 1.5B 70–75%（单调） |
| 显著性判定 | 单位错误，5pp 被判成超噪声 | 用 95% CI 重叠判断 |
| 质量底线 | 3pp（比噪声紧）→ 只剩 1 格可选 | 6pp（≈1 CI 半宽）→ 可选集恢复 |
| 长文档场景 | "无可行配置"（无解释） | "预测 1576 ms > 1500 ms 上限"（可解释） |

# 第七轮：真跑"不可行格"，把一条结论整个改写了

## 三十、我原来的判断错在哪

报告里写着"15 个格因显存/上下文不可行"。这是**估算**，不是实测。
`--include-infeasible` 真跑之后：

- **14 个跑通了**，只有 1 个真 OOM
- 跑通的那些吞吐掉 2.6–4.3 倍，显存停在 7.7–7.9 GB

原因：llama.cpp 默认 `--kv-offload`，KV 装不下就**静默搬到主机内存**。

**教训**：凡是"跑不了"的结论，都应该真跑一次再说。
估算剪枝给出了正确的答案，但**理由错了**——不是"不能跑"，是"能跑但会静默降级"。
这两句话在工程上的分量完全不同：前者是约束，后者是陷阱。

## 三十一、连带修正的两个判据错误

| 错误判据 | 后果 | 正确判据 |
|---|---|---|
| `ctx × 并发 > 32768` → 视为 KV 外溢 | 误判 2 个正常格（1.5B/3B 在 ctx8192 c16，KV 只有 3.8/4.8 GB，装得下，吞吐反而略高） | **KV 是否装进 8 GB**（`cfg.kv_fits_vram`） |
| 认为 15 格全是"不可行" | 少拿了 7 个合法数据点 | 7 格进主数据集（45→52 格），7 格作悬崖证据 |

## 三十二、PEAK 的真相：decode 与 prefill 不是同一个数

原本以为 `PEAK` 是一个机器常数。用后端基准把并发推到 64 后发现：
decode 反推 ≈ 9 TFLOP/s，prefill 反推 ≈ 31.6 TFLOP/s。

物理原因：decode 是 batch×1 的瘦长矩阵乘（GEMV 类），张量核难以喂满；
prefill 是一次大 GEMM，效率高得多。

拆成两个参数后：最大误差 19.5% → 15.3%，算力受限格从 0/12 变 1/12。

## 三十三、仍然没做到的

**在单机 8 GB 上无法把 decode 推到算力饱和点。**
并发 64 时后端 2963 t/s，距 `PEAK/(2P)=10,300` 还差 3.5 倍；
而 1.5B 在并发 64 时 KV 已占 0.59 GB，再往上会先撞显存。

这条要如实写进局限：**"算力拐点"是在 8 GB 单机上不可达的实验**，
不是我没做，而是这个硬件上做不到。

# 第八轮：加密并发，逼出两个系统性错误（一个测量、一个物理）

## 三十四、测量口径：吞吐被"波次数"污染

加密并发后立刻出现非物理现象：吞吐非单调。
根因是我的 `requests_per_repeat()` 给每个并发配了不同数量的请求
（16/24/32/48/64），导致波次数从 16 波到 1.33 波不等。
波次少 → 测量窗口里收尾空闲占比大 → 吞吐被低估最多 23%。

**修正**：改用稳态口径（并发 × 生成长度 ÷ 平均单请求生命周期），
它与波次无关，且正是解析模型预测的量。MAPE 11.28% → 8.70%。

**教训**：任何"总时间 ÷ 总量"的指标，都必须先检查分母的时间窗里有没有空闲。
顺带发现：`requests_per_repeat` 应该按波次数恒定来设计（例如恒定 4 波），
而不是按并发给一个拍脑袋的数。

## 三十五、物理：服务开销随并发非线性

按是否标定过分组：

| 分组 | 格数 | 成本 MAPE |
|---|---|---|
| 标定过的并发（1/4/16/32） | 33 | 5.8% |
| 未标定的并发（2/8/12/24） | 35 | 11.5% |

TPOT 的形状暴露出非线性的具体形式（7B-Q4 / ctx512）：
并发 4→8 涨 63%（23.7→38.7 ms），但 8→16 几乎不变（38.7→39.0 ms）。

`c_srv·b` 是线性的，因此在中间并发点系统性低估 20–34%。

**我选择不硬拟合**（加参数去追一个台阶，等于用 12 个标定点过拟合服务端的实现细节），
而是把**适用域**写清楚：标定过的并发点可直接算，中间值必须实测。

这不是退让，是更强的结论：**容量规划最常选的恰恰是中间并发，而那里必须实测。**

## 三十六、现在的状态

- 数据：80 格 / 240 行，0 失败，全程满频
- 模型：6 参数；标定并发上 MAPE 5.8%，全留出集 8.70%
- 已明确记录三条适用边界：并发中间值、KV 外溢、算力饱和不可达

# 第九轮：一次假设被推翻，一次预测被打脸，但论点更强了

## 三十七、我上一轮的归因错了一半

上一轮我把"并发 8 处 TPOT 异常"归因于**波次数不同**（prefill 与 decode 重叠）。
做了对照实验（并发固定 8，请求数 8/16/32/64）后：

**TPOT 极差只有 2.4%，与波次无关。**

错在哪：我把两件事混成了一件。
- **墙钟吞吐**确实被波次污染（收尾空闲占比），必须改用稳态口径；
- **TPOT** 是逐请求量出来的，完全不受波次影响。

**教训**：一个"异常信号"往往同时由两个原因造成。
先别急着归因，先设计一个能把两者分开的实验——这次分开之后，
一个被排除，另一个反而被确认为真实现象。

## 三十八、预测打脸：0.5B 并没有进入算力受限区

我的推理：0.5B 权重小，并发 64 时访存只要 2.6 ms、算力要 4.75 ms，所以算力先到。
实测：吞吐在并发 32 就饱和（1423 t/s），此后下降；而它距离算力下限还差 9.5 倍。

**我漏掉的是 `c_srv × 并发`**：
并发 64 时这一项等于 49 ms，是算力时间（4.75 ms）的 10 倍，占 TPOT 的 88%。

**教训**：在"谁先饱和"的推理里，只要有一项随并发线性增长、而且是**加**上去的，
就不能只看 max(访存, 算力)。我连着两轮在这上面栽同一类跟头——
第一轮是 1.5B 的"算力拐点"，这一轮是 0.5B 的"算力拐点"。

## 三十九、这一轮真正的产出

不是"又证明了服务路径是瓶颈"，而是：
1. **排除了一个错误归因**（波次），避免了把真实效应当成测量噪声；
2. **量出了台阶的形状**（陡—平—陡），解释了为什么中间并发误差大；
3. **第三次独立验证**了核心论点——用比 7B 小 15 倍的 0.5B。

第 3 条最值钱：如果 0.5B 这么大的模型也被服务路径卡住，
那就不是"模型太大导致跑不动"，而是**这套部署实现的固有开销**。
这个区分直接决定该优化什么：不是换模型，是换服务栈。

# 第十轮：一次实验自证无效，但换方法后得到了更硬的结论

## 四十、我的"四变体对照"设计错了

为了拆 c_srv，我设计了 chat/原生 × 流式/非流式 四组对照，
差值是 515/146/592 ms，看起来能算出"推流成本"和"模板成本"。

但两个缺陷让它整体无效：
1. **顺序固定**：B/C/D 都排在 A 后面，享受了预热收益；
2. **工作量不一致**：A 组中位输出 122 token，其余 128 token。

## 四十一、日志法救回来，而且结论反转

llauna-server 每个任务会打印自己的 `eval time per token`。
把**同一批请求**的服务端时间与客户端 TPOT 相比：

| 并发 | 客户端 TPOT | 服务端 eval | 交付开销 |
|---|---|---|---|
| 1 | 9.7 | 9.7 | −0.0 |
| 32 | 39.5 | 40.0 | −0.5 |

**交付开销在所有并发下都是 0。**

所以原来的"HTTP/推流是瓶颈"是错的——`c_srv` 全部在 decode 循环内部。

**教训**：当两种方法给出相反结论时，不要挑顺眼的那个，
要去看哪种方法控制了混杂变量。日志法比对照法强，是因为它不依赖实验顺序。

## 四十二、副产物：解释了"陡—平—陡"

每并发流的额外开销：1.18（c1）、1.07（c4）、**1.38（c8）**、0.94（c16）、0.78（c32）。

**峰值在并发 8**——这正是增补 C 里 TPOT 在那一段变陡的原因。
不是"台阶"，是"每流开销随并发变化"。

# 第十一轮：四项外部效度，两项成立两项打折

## 四十三、跨模型族成立（12.7%）

换 Llama-3.2-1B（不同层数、不同 GQA 结构、不同词表），**一个参数都不重标定**，
平均误差 12.7%。这是本项目最"硬"的一条外部效度证据。

## 四十四、泊松到达推翻了我的一个假设

我一直以为同步波次是最坏情况。实测：泊松到达下 TTFT 是模型预测的 2–8 倍。

原因不是模型错了，而是**模型只算服务时间，不算排队时间**。
同步波次里所有请求同时进入、没有排队，所以它是最乐观的情形。

这条必须写进局限，而且要写成"模型不能直接用于容量规划"，
而不是含糊地说"负载画像简单"。

## 四十五、CPU 迁移：方向对，精度不够

标定三个硬件常数后，同并发跨模型的留一误差 27%（22–32%）。
不是不能用，但**不能像同机那样直接决策**。

另外一个发现：把 c_srv 也放开重拟合，CPU 上得到 2.06 ms（GPU 0.766），
但误差只从 66.4% 降到 63.0% —— 说明 c_srv 更像吸收残差的项，
这与第十轮"c_srv 在 decode 循环内部"的结论互相印证。

## 四十六、这一轮的方法论收获

1. **对照实验必须同批、交替、顺序随机**。KV 量化第一版跨批次比，
   数据已经被删掉，只能推翻重来。
2. **"最坏情况"要先验证**。同步波次被默认成上界，实测是最乐观情形。
3. **负结果比正结果更需要写清楚**。27% 和 66% 都留着，不挑好看的报。

# 第十二轮：质量轴重做——我上一轮的结论被自己推翻

## 四十七、错在哪

上一轮我写"质量上五组置信区间全部重叠，换大模型的收益没被显著测出"。
第三轮审计指出：**模型答的是同一批题，应该用配对检验**。
我照做后，结论反转：45 对里 32 对显著，7B（91.0%）显著优于所有其他组合。

我错在两点：
1. 用**独立** Wilson 区间比较**配对**数据——方差被高估，灵敏度被浪费；
2. 140 题的样本量本来就不够，我却用它下了"无差异"的结论。

## 四十八、扩题后的三个新发现

1. **Q2 量化是灾难**：1.5B-Q2 只有 30.2%，比 Q4 低 52 个百分点。
2. **Q4 ≈ Q8**：没有显著差异（p=1.00），而 Q8 权重多 1.7 倍 → 能用 Q4 就别用 Q8。
3. **`reverse` 题型全模型 0%**：不提供区分度，是基准的已知缺陷，下版要换掉。

## 四十九、结论形态也变了

原来推荐器给"一个配置"，现在改成**质量—成本权衡表**：

| 质量损失 | 配置 | 成本 |
|---|---|---|
| 0–6 pp | 7B-Q4 | 20847 |
| 8 pp | 3B-Q8 | 4919 |
| ≥10 pp | 1.5B-Q4 | 2182 |

成本差 9.6 倍换 9.6 个百分点质量 = **每 1 点质量贵 27%**。

**"能接受多少质量损失"是业务决策，不是模型该替你决定的事。**
承认这一点，比声称"最优配置是 X"更专业。

## 五十、第四次被推翻

前三次分别在第 5、7、9 轮。这次推翻的是我自己上一轮刚写进报告的话，
而且动力来自一条方法学修正（配对检验）。
说明流程是有效的：**只要检验方法在进步，结论就该继续被推翻。**

# 第十三轮：把"后悔值"这个指标自己给否了

## 五十一、我原来那句话站不住

报告里曾写："决策后悔值 3.3%，说明用模型决策几乎和用全量实测决策一样好。"

第三轮审计的 E 条指出：只有 4 个场景、基线是稻草人、最优解全在 SLA 边界、
成本面平坦 → 后悔值天然就小，**证明不了排序能力**。

我把场景扩到 16 个、加了 bootstrap 区间、按 5 个质量档位分开算。
结果：**后悔值仍然≈0**。

## 五十二、但原因和我想的不一样

不是"模型排序能力强"，而是：

> 一旦固定质量档位与 SLA，成本最优解几乎完全由"最小可用模型"决定，
> **这个问题本身就没有排序难度**。

所以"后悔值≈0"是一个**关于问题结构的结论**，不是关于模型能力的结论。
把它当成能力证明，是我原来的逻辑错。

## 五十三、指标用错了，但项目没变差

模型真正贡献的三件事变得清楚了：
① 预测绝对成本（差一个量级就会选错档）；
② 量化质量汇率（每 1 点质量贵约 27%）；
③ 判断可行性边界（"7B 质量 + 300 ms"在 8 GB 卡上不存在）。

**一个诚实的项目，应该主动指出现有指标证明不了什么。**
这一轮删掉的是一句过硬的表述，换来的是一句经得起追问的表述。

# 第十四轮：把"测量故障"这个判断本身否掉了

## 五十四、我误判过一次

上一轮我写："泊松 λ=4/6 都只达成 2.6 qps → 客户端自己成了瓶颈，
TTFT 差 2–8 倍的尾端不可信。"第三方复核也给了同样判断。

本轮交叉验算：

```
服务能力 = 并发 ÷ 单请求耗时 = 8 ÷ (463.8 + 128×19.9) ms = 2.66 请求/秒
```

**2.63–2.65 的达成值 = 服务能力。** 所以那是服务器饱和，不是测量故障。

我犯的错：**看到一个"达不到目标"的数字，先假定是工具坏了**，
而没有先用已测数据把它算一遍。

## 五十五、顺带发现自己的单位错

分析脚本把 `并发 ÷ 单请求耗时` 写成了 `并发 × 生成长度 ÷ 单请求耗时`，
结果放大 128 倍 → "实测/预测 = 0.01" → 更像"客户端瓶颈"了。

两个错误方向一致，互相强化，差点把一条正常结论永久写死。

## 五十六、重做后的结论比原来强

1. 吞吐天花板 2.49 请求/秒；延迟膝点在 λ=2（p90 涨 9.9 倍）——两个数差近一倍；
2. 模型给容量上界 3.43，实测/预测 = 0.73 → **可用于容量规划**（乘折减系数），
   推翻了我原来"不能用于容量规划"的说法；
3. **新发现**：泊松到达下 TPOT 比同步波次高 25%（19.9 → 24.9 ms），
   原因是每个新请求的 prefill 打断 decode——模型未刻画的一项。

## 五十七、第五次被推翻

第 5、7、9、12 轮各一次，这是第 13 次修正记录里的第五次结论反转。
这次推翻的是**我上一轮刚下的"测量故障"判断**，以及报告里"不能用于容量规划"那句话。

规律很清楚：**每次我想"这条先放着"，它就会在下一轮变成错误。**
所以宁可当时多验一遍。

# 第十五轮：这次是往好的方向翻——被我否掉的指标其实是对的

## 五十八、我上一轮说错了

审计第 52–53 节我写过：

> "一旦固定质量档位与 SLA，成本最优解几乎完全由'最小可用模型'决定，
> 这个问题本身就没有排序难度。所以后悔值≈0 是关于问题结构的结论，不是模型能力的结论。"

**这个推理错了。** 第二轮复核指出：要给这个指标加负对照才能下结论。

## 五十九、负对照的结果

| 选择策略 | 后悔值中位 | 均值 | 最大 |
|---|---|---|---|
| 六参数模型 | 0.0% | **0.1%** | 3.9% |
| 随机选 | 281.4% | **268.3%** | 533.6% |
| 选最大模型 | 762.5% | **813.4%** | 1587.3% |
| 参数 ±0.5σ 扰动后重选 | 0.0% | 0.1% | 3.9% |

**乱选平均多付 2.7 倍，按"越大越好"多付 8.1 倍。**

所以"后悔值≈0"不是指标空了，而是模型真的选对了。
同一档位内仍有很多格（不同 ctx/并发），选错一样很贵——**排序难度是存在的**，
只是我的模型把它解决了。

## 六十、还有一条意外收获

参数按 ±0.5σ 扰动后重选，后悔值仍是 0.1%——**决策对参数不确定性不敏感**。

这一点值得单独说：`ovh_ttft` 的 bootstrap 区间宽达 141%（几乎估不准），
但它估不准**不影响选谁**。所以"参数不可辨识"不一定意味着"决策不可靠"，
这两件事要分开评估。

## 六十一、教训

**"这个指标没用"是一个需要证据的判断，不能靠推理下。**
我上一轮用"候选集粗"直接推出"指标无分辨力"，
而正确的做法是跑一组对照——成本只有 10 分钟，结论却完全相反。

这已经是第六次自我修正，也是第一次**往好的方向翻**：
前五次都是"我以为对了，其实是错的"；这次是"我以为错了，其实是对的"。

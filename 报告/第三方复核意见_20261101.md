## 2. 优点（每条都有实证支撑）

### 2.1 数据是真实的，而且干净得罕见

324 次会话级测量、11760 个请求零失败、全程满频、每个请求都有逐 token 时间戳与 `t_start_rel/t_end_rel`。`logs/` 里的 llama.cpp 原生输出可以与 `raw_cells.jsonl` 的数字逐条对账。这在学生项目里非常少见。

### 2.2 测量纪律落进了代码，不只是写在文档里

- 每请求注入随机前缀 + `cache_prompt: false`（防 prompt cache 把 TTFT 打成 0）
- `ignore_eos: true` 强制生成 128 token（保证 TPOT 可横向比较）
- 每格预热 2 个请求并丢弃
- 每格 3 轮取**中位数**
- **时钟与功耗双低才判降频**（只看功耗会把高并发下的空转误判成降频——这个判据是对的）
- `tc_probe.py` 用服务端自己回报的 `truncated / tokens_evaluated` 反验 `--ctx-size` 语义
- 客户端 CPU 占用监控（防止"测出的是 Python 脚本的速度"）

这套东西体现的是"懂测量"，比"会调包"值钱得多。

### 2.3 最有价值的发现：`c_srv` 与"交付开销 ≈ 0"

三向分解（客户端 TPOT − 服务端 eval − 硬件下限）给出 **0.77–1.38 ms/流/步**，并且：

| 并发 | 客户端 TPOT | 服务端 eval | 硬件下限 | decode 内开销 | 交付开销 |
|---|---|---|---|---|---|
| 1 | 9.7 | 9.7 | 8.5 | 1.2 | **−0.0** |
| 32 | 39.5 | 40.0 | 15.0 | 25.0 | **−0.5** |

再用独立的 `llama-batched-bench`（绕开 HTTP）佐证"服务路径只达后端吞吐的 40–48%"。**"瓶颈不在网络层，在 decode 循环内部"**是一个有分量的工程结论。

### 2.4 第二个真发现：显存边界是"性能悬崖"

KV 装不下时 llama.cpp **静默 offload、不报错，只是慢 2.6–4.3 倍**；KV 量化在 KV 主导时（1.5B）+238%，权重主导时（3B/7B）无效。这是一个有实操价值、且容易被忽略的点。

### 2.5 模型简洁、有物理含义、确实做了留出验证

两条公式、6 个参数、12 格标定、68 格留出，标定并发上 5.8%——这是能工程用的精度，且参数每一个都能指出一项物理机制。

### 2.6 科学态度在同级里罕见

- README 专列"这个模型能信到哪"（适用边界表）
- 报告里有"三次被数据推翻"一节
- 上级目录有 733 行对抗性自审记录，含一个被自己发现并修掉的致命 bug（`--ctx-size` 语义）
- `_selftest/` 里假数据被明确标注"禁止写进报告"

这种自我否定式文档，在保研/求职材料里非常稀缺。

### 2.7 统计意识方向正确

对数比损失、t 分布 + 自由度校正、Wilson 区间、可辨识性诊断、NaN 处理……虽有小错（见下文），但方向是对的，说明作者知道"要报不确定性"。

### 2.8 交付物齐全

README / 两页技术报告 / 10 篇手册 / 简历条目 / 答辩稿 / 迁移一页纸 / CLI 推荐器 / 5 张图。包装能力是明显强项。

## 3. 不足（按严重程度分级）

### A. 【致命】对外数字与仓库产物不一致，一跑就露馅

| 材料上写的 | 实际跑 `python code/tc_model.py` |
|---|---|
| 留出 **68 格**，成本 MAPE **8.70%** | 留出 **76 格**，MAPE **9.08%** |
| 90% 区间覆盖率 86.8% | **85.5%** |
| （未提及判定） | 打印 **"MAPE 未达标 \| 最大误差 未达标"**，`fit.json` 里 `"passed": false` |

**根因**：8 个 Llama 跨模型族格（`_xf`）被混进了留出集。报告把"跨族 12.7%"当作**单独一项外推证据**，但代码只排除了 `_w*` 与 `_n*` 探针格，`_xf` 默认计入留出集。

同类漂移还有一串：

| 位置 | 文档写的 | 实际 |
|---|---|---|
| README / 交接清单 | 100 个配置格 / 300 次测量 | 108 格 / 324 次 |
| 交接清单 | 80 格 × 3 轮 = 240 行 | 108 格 × 3 = 324 行 |
| README / 交接清单 | 21 个脚本 | 26 个 |
| README / 报告 | 服务开销占 TPOT 57%、最高 77% | 当前数据 60%、最高 80% |
| README | 决策后悔值 3.3% | 三个有解场景为 0.0% / 0.9% / 3.3% |
| `figures/fig4` | 图内标注"留出（76 格）" | 与 README 的 68 格肉眼可见地打架 |

**这是最伤的一条**：项目全部声誉押在"诚实"上，而最容易被验证的地方恰好对不上。哪怕不是故意的，后果一样。

---

### B. 【重要】"成本 MAPE"不是独立验证，是 TPOT 误差的换算法

稳态成本的定义是：

```
steady_cost = 1e6 · (TTFT + GEN·TPOT) / (b · GEN)
```

而模型预测的**正是** `(TTFT + GEN·TPOT)`。于是成本误差与 TPOT 误差高度同源：

| 指标 | 数值 |
|---|---|
| 留出集 cost MAPE（稳态口径） | 9.08% |
| 留出集 TPOT MAPE | 9.02% |
| 两者残差相关系数 | **0.83** |

用**真实墙钟吞吐**（含收尾空闲、波次效应，是生产里真正付的钱）做目标重算：

| 口径 | 成本 MAPE | 最大误差 |
|---|---|---|
| 稳态（模型自身定义） | 8.70% | 24.2% |
| **墙钟（独立口径）** | **11.28%** | **35.1%** |

**建议表述**："稳态推导口径 8.7%，端到端墙钟口径 11.3%"，而不是把 8.7% 当作"端到端成本预测"。这不丢分，反而显得懂"口径"这件事。

---

### C. 【重要】质量轴统计上是空的，却决定了最终推荐

**C1. 测不出差异。** 140 题的结果：

| 模型 | 准确率 | 95% CI |
|---|---|---|
| 7B-Q4 | 81.4% | [74, 87] |
| 3B-Q8 | 77.1% | [70, 83] |
| 3B-Q4 | 76.4% | [69, 83] |
| 1.5B-Q4 | 75.0% | [67, 81] |
| 1.5B-Q8 | **70.0%** | [62, 77] |

1.5B-Q8 甚至比 1.5B-Q4 还低，**五组 CI 全部重叠**——质量上分辨不出任何两组。

**C2. 但推荐器用硬阈值剪枝。** 默认 `--min-acc-drop 6`，阈值 = 81.43% − 6pp = **75.43%**，而 1.5B-Q4 = **75.00%**，**只差 0.43pp 就被剪掉**。

**C3. 这个阈值决定结论。** 把阈值改成 7pp 再跑：

| 阈值 | 推荐配置 | 预测成本 |
|---|---|---|
| 6pp（默认） | 3B-Q4 / ctx2048 / c4 | 3402 |
| **7pp** | **1.5B-Q4 / ctx2048 / c4** | **2182（−36%）** |

也就是说，**整个"质量—成本权衡"的结论，由一个远小于测量噪声（±6pp）的 0.43pp 决定。**

**C4. 题集本身是窄的。** 140 题全是算术类（加法/乘法/比大小/排序/倒序/计数），测的是"算术能力"而不是"通用质量"。

**C5. 两处 NaN 逻辑相反。**

- `tc_recommend.py`：无质量数据的组合 → 比较结果为 False → **静默剔除**
- `tc_analyze.py` 的 Pareto：无质量数据 → 视为 **通过**

后者直接导致了下一条。

### D. 【重要】`figures/fig5` 正在直接反驳报告结论

报告写："48 个满足质量底线的配置中仅 **7 个**位于 Pareto 前沿，且**全为 3B-Q4**。"

我用 core-only 口径复算，**这句话是对的**（48 参与 / 7 前沿 / 全 3B-Q4）。但仓库里那张图的前沿是：

```
0.5B_q4_k_m_ctx512_c1_w4   cost 3066
0.5B_q4_k_m_ctx512_c2_w4   cost 1735
0.5B_q4_k_m_ctx512_c4_w4   cost 1152
0.5B_q4_k_m_ctx512_c8_w4   cost  980
0.5B_q4_k_m_ctx512_c16_w4  cost  785
0.5B_q4_k_m_ctx512_c32_w4  cost  703   ← 6 个点全是 0.5B
```

原因：0.5B 从未做质量评测（`acc` 为 NaN），而 NaN 被当成"通过"；同时 0.5B 又最便宜。**面试官看一眼图就会问："为什么一个没做过质量评测的 0.5B 模型是最优解？"**

---

### E. 【重要】后悔值 / 降本证据偏弱

`verify_recommendation.csv` 的四个场景：

| 场景 | 推荐 | 后悔值 | 相对基线降幅 |
|---|---|---|---|
| 实时对话（严格） | 3B-Q4 / c1 | 0.88% | —（基线不满足 SLA） |
| 通用问答（宽松） | 3B-Q4 / c4 | 3.27% | 18.0% |
| 长文档摘要 | **（无可行配置）** | — | — |
| 高并发批处理 | 3B-Q4 / c8 | 0.00% | 36.5% |

问题：

1. 4 个场景里 **1 个无解、2 个结果完全相同**，真正独立的只有 2 个；
2. **基线是稻草人**：`3B-Q8/ctx2048/c4` 本身又贵又不是最优，候选里早就有更便宜的 1.5B；
3. **最优解全落在 SLA 边界**（"满足 SLA 的最大并发"），成本面平坦 → 后悔值天然就小，**证明不了模型的排序能力**；
4. 后悔值只在 4 个点上算，**没有置信区间**；
5. README 写"降幅 18%"，实际是 18.0%–36.5% 里的最小值，且只在 2 个场景成立。

---

### F. 【次要但真实】两个"外推证据"口径不清

**F1. 跨模型族 12.7%。** 这是 **TPOT 与 TTFT 平均绝对误差**，不是成本 MAPE，与主指标不同口径。且 Llama 的 TTFT 在并发 1 时系统性 **+25%**（说明 `ovh_ttft` 是模型族相关的，模型没提这一点）。

**F2. 泊松到达探针的负载生成器饱和。** `probe_poisson.csv`：

| λ | 实际达成 qps | 平均并发 | TTFT 实测/预测 | TPOT 实测/预测 |
|---|---|---|---|---|
| 2 | 2.00 | 7.3 | 2.05× | **1.53×** |
| 4 | **2.63** | 16.6 | 6.02× | 0.99× |
| 6 | **2.65** | 21.0 | 8.14× | 0.83× |

λ=4 与 λ=6 的达成率都是 ~2.65 qps → **后两个点实际是同一负载**，"TTFT 差 2–8 倍"的尾端不可靠；同时 **"TPOT 准"不成立**（λ=2 时差 53%）。

### G. 【重要】6 个参数里 2 个基本不可辨识

我算了最优点处的 Hessian：

| 检查 | 结果 |
|---|---|
| 条件数 | **2.8 × 10⁴**（严重病态） |
| `BW` 变动 ±15% | loss × 1.9–2.3（强约束） |
| `PEAK_pre` ±15% | loss × 2.5–3.0（强约束） |
| **`PEAK_dec` ±15%** | **loss 只变 ×1.04–1.08**（几乎不可辨识） |
| **`ovh_ttft` ±30%** | **loss 只变 ×1.14**（弱约束） |

也就是说，**13.2 TFLOP/s 和 15.96 ms 这两个数是"拟合出来好看"，不是"测出来的"**。代码只提示"1/12 个格处于算力受限区"，没有量化到"这两个参数不可信"。报告里应当给区间，或明确写"4 个可辨识 + 2 个弱约束"。

### I. 【边界】单机单栈、合成负载，外推有限

- 128 token 固定生成、约 296 token 提示、同步波次 —— 不是真实业务流量；
- 只有一张 RTX 4060 Laptop + llama.cpp，跨硬件只做了 CPU（27%）；
- 模型不含排队，项目自己也承认"不能做容量规划"，但标题与简历条目仍像"成本模型"；
- "迁移一页纸"目前仍是**主张**：CPU 迁移只有 27% 误差，不足以支撑"只需重标定两个常数"。

## 7. 非技术风险提示：AI 协作的透明度

项目计划书里明确写着"已产出的实测数据（助手代跑，供本人复核）"，代码注释密度与文档风格也高度一致。这带来两个风险：

1. **若简历写"独立完成"**，需要能对"12 问"逐条展开、并对每个数字的来源给出解释；
2. **面试官最容易问的三个点恰好是现在的软肋**：
   - "8.70% 是怎么算的？能现场跑一遍吗？"（复现出来是 9.08%）
   - "为什么 Pareto 前沿全是 0.5B？"（图与结论矛盾）
   - "质量尺度差别不显著，为什么还据此剪枝？"（阈值 0.43pp 决定结论）

**最低成本的补课方式**：亲手重跑一次 core 网格（约 50 分钟）＋自己改一遍数字生成脚本。这样"每个数字从哪来"才有肌肉记忆。

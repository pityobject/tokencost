## F10 · 2026-11-04 · `tc_profile` 拟合失败：TTFT/TPOT 在并发维度与仓库数据不符

**现象**

`tc_profile` 在真机上跑完 12 格，c1 的三个长度与仓库数据**几乎完全吻合**：

| 格 | 本次 | 仓库 |
|---|---|---|
| c1/L183 | TTFT 53.0 ms | 52.8 ms（L177） |
| c1/L542 | 134.0 ms | 133.9 ms（L536） |
| c1/L1978 | 431.5 ms | 426.3 ms（L1973） |
| c1 TPOT | 9.76 / 9.95 / 10.31 | 9.70 / 9.77 / 10.04 |

但**并发维度严重偏高**：

| 格 | 本次 TPOT | 仓库同类 |
|---|---|---|
| c2/L542 | 14.77 ms | 10.69 ms（c2/L537） |
| c4/L542 | 32.93 ms | 12.84 ms（c4/L537） |
| c8/L542 | **67.78 ms** | **21.23 ms**（c8/L537） |

结果拟合出 `BW = 642 GB/s`（真值 249）、`c_srv = 6.66`（真值 0.77）、
TTFT MAPE 22.5%、TPOT MAPE 37.3%——参数全部失真。

**根因（已定位两个，剩一个待验）**

1. ✅ **服务端配置确实有影响**：把 `-np 16 / 每槽 2112` 换成仓库的 `-np 8 / 每槽 8192` 后，
   c8 的 TPOT 偏差从 **3.2 倍降到 1.4 倍**（67.8 → 30.3 ms，仓库 21.2）。
2. ✅ **每格请求数必须随并发增加**：仓库是 `c1=16 / c4=24 / c8=32 / c16=48 / c32=64`，
   而本工具固定发 16 个。高并发下只有 1–2 波，测到的是**爬坡期争用**而非稳态，
   TPOT 系统性偏高。已在 `tc_profile` 改为调用 `cfg.requests_per_repeat(conc)`。
3. ✅ **TPOT 的终点取错了**：仓库用 `(t_last - t_first)/(n_out-1)`，
   我用了 `(t_end - t_first)`——`t_end` 含 HTTP 收尾与 usage 块，
   高并发时尾巴更大，把 TPOT 算高 2–3 倍。修正后 TTFT MAPE 从 65% 降到 **1.1%**。
4. ✅ **标定计划不能包含模型的失效区**：长 prompt（>1000）× 高并发（≥4）下
   TPOT 实测比模型高 2–4 倍（这正是附录 K.5 的发现，现在被第二个仪器独立复现）。
   把这些格子放进标定集，优化器会为了妥协它们而扭曲全部参数。
   已改：并发维度用中短 prompt，长度维度只用 c1，并加了越界警告。

**最终结论（诚实版）**

| 参数 | 真值 | `tc_profile` 反推 | 判定 |
|---|---|---|---|
| `BW` | 249.1 GB/s | 262.9 | ✅ +5.5% |
| `PEAK_pre` | 31.9 TFLOP/s | 28.6 | ✅ −10% |
| `ovh` | 16.0 ms | 11.4 | ✅ −29%（可接受） |
| **`c_srv`** | 0.766 | **1.58** | ❌ 2× |
| **`b_sat`** | 13.3 | **6.6** | ❌ 0.5× |

`c_srv × b_sat` 的**乘积是对的**（1.58×6.6=10.4 vs 0.766×13.3=10.2），
但两者分不开——而且 `c_srv` 的估计**依赖于你在哪些并发档上标定**：
c8 正好落在 c4→c16 的台阶上，把它放进标定集，`c_srv` 就会被拉高约 2 倍。

**规则（已写进工具帮助与自标定指南）**：
> 标定网格要与你实际服务的并发档一致；本项目的模型是在 **1/4/16/32** 上拟合的，
> 所以自标定也应优先用这四档。

**怎么发现的**

不是靠自检（`--selftest` 用合成数据，永远绿），而是**拿真机结果与仓库同条件数据逐格对比**——
c1 全中、并发全偏，这个"只在某个维度偏"的形态就是线索。

**下一步（待做）**

同一个工具、两种服务端配置做 A/B：

```powershell
# 配置 B：与仓库一致（8 槽，每槽 8192）
python tc_server.py 3B q4_k_m 8192 8
python tc_profile.py --base-url http://127.0.0.1:8090/v1 --spec 3B:q4_k_m \
  --concs 1,2,4,8 --lengths 512 --per-slot-ctx 8192 --slots 8
```

若 B 的 c8/L≈540 TPOT 回到 ~21 ms → 是服务端配置；
若仍是 ~68 ms → 是工具的负载形态（需改用 `tc_loadgen.run_load`）。

**教训**

- **自检只能证明"算式对了"，证明不了"测量对了"**。必须在真机上与已知数据对账。
- 对比要**逐格**，不要只看总 MAPE——"c1 全中、并发全偏"比"22.5%"信息量大得多。

## F9 · 2026-11-04 · `tc_profile` 的 TTFT 测的是**缓存命中**，不是 prefill

**现象**

首次真机跑：c1/L126 的 TTFT = **13.6 ms**，而 TPOT = 10.0 ms。
TTFT 几乎等于一个 token 的解码时间——物理上不可能。
同时 prompt 长度也不对：目标 512 → 实测 378，目标 2048 → 实测 1350。

**根因**

1. 16 个请求用的是**同一个 prompt** → 从第 2 个起 llama-server 的 prompt cache 命中，prefill 时间≈0；
2. 请求里没传 `cache_prompt: false`；
3. 长度换算用了 0.95 token/字，实际中文约 0.65。

**怎么发现的**

`TTFT ≈ TPOT` 这个不等式——**快得离谱本身就是信号**。
另外与仓库同条件数据（c1/L177 = 52.8 ms）差 4 倍。

**修复**

- 直接复用仓库已有的 `tc_loadgen.make_prompt(target, nonce)`（每次不同前缀）；
- payload 加 `"cache_prompt": False`；
- 每个请求独立 nonce（`nonce = hash(conc, L) + i`）。

**教训**

> `tc_loadgen.py:42` 的注释里早就写着："一定要每次都不一样（加 nonce），否则 prompt cache 会命中，
> prefill 时间会变成 0，你的 TTFT 数据就全废了。这是新手最容易踩的坑。"

**我造了个新轮子，然后踩了同一个坑。**
→ 新工具第一原则：**先看仓库里有没有现成实现**。

**现象**

**教训**

看到"一个数正好等于预期"时，要问它**是配置给的还是默认行为**。

## F7 · 2026-11-04 · 应用题"全员 2%"：题目答案算错

**现象**

新增的多步应用题，10 个组合平均准确率 **2.0%**（7B 只有 10%）。

**根因**

题目生成器把"还剩多少"的答案写成了 `a + b*c`，而语义是 `a - b*c`
（17 元买 4 本 6 元 → 算出 −7）。**题干和答案对不上，模型怎么算都判错。**

**怎么发现的**

"全员都这么差"本身就可疑。抽查实际回答，发现模型给的是 11、5、6 这类数——
它们更像"算错了"，而不是"没作答"。

**修复**

改为 `a - spent`，且保证 `a > spent`；重跑得 **8.0%**（仍低，但原因变成"禁止打草稿"）。

**教训**

> **看到"全员都很差"，第一反应必须是"我的测量错了吗"。**
> 修正后 8.0% 与错误版 2.0% 的**解释完全不同**：前者是设计选择，后者是题目 bug。

## F6 · 2026-11-03 · 后悔值半宽公式不一致（差 36.5 倍）

**现象**

`tc_verify.py` 与 `tc_regret_controls.py` 用 `0.5*log(1+σ²)`（→1.0045），
推荐器用 `fit["half_width_log"]`（→1.177）。同一问题，两套答案。

**根因**

"预测区间半宽"被实现了两遍。前者是 lognormal 的均值换算项，**不是区间**。

**修复**

统一到 `tc_common.half_log()`；后来更进一步，把候选集也统一到 `tc_common.rank()`。

**教训**

同一个概念只能有一个实现。**第三轮复核后建立了 `tc_common.py`，就是为了这个。**

## F2 · 2026-10-31 · 把显存边界当"硬墙"，其实是"性能悬崖"

**现象**

显存装不下的格子被标记为"不可行"。

**根因**

llama.cpp 在 KV 装不下时**静默把 KV 搬到主机内存**（`--kv-offload`），
不报错，只是慢 2.6–4.3 倍。所以"装不下"不等于"跑不了"。

**怎么发现的**

14 个标"不可行"的格子里，有 7 个实际能跑，只是慢。
**对照 `mem_used` 与吞吐才发现是降级，不是失败。**

**修复**

改用 `cfg.kv_fits_vram()` 判定；把"性能悬崖"写进适用域；加"时钟与功耗双低即作废"的闸门。

**教训**

**"报错"是一种善意。静默降级才是最危险的失败模式。**

## F1 · 2026-10-30 · 三参数模型：MAPE 33.5%，并发 32 低估到 0.39

**现象**

第一版只有"带宽 + 算力 + 固定开销"三项，留出集误差 **33.5%**，最大 71.5%。

**根因**

漏掉了"每条并发流每步的服务开销" `c_srv` 与 prefill 饱和项。

**怎么发现的**

不是调损失函数，而是看硬件计数器：**GPU 利用率 89%→48%、功耗 79→49 W** —— 显卡在空转。
再用 `llama-batched-bench` 绕开 HTTP 测后端：并发 32 时后端 2377 t/s，服务路径只有 940（**40%**）。

**修复**

加 `c_srv·b` 与 `min(b, B_SAT)`，误差 33.5% → 8.70%。

**教训**

> 模型不准时，**先去看硬件计数器，不要先去调损失函数**。

## F11 · 2026-11-04 · 同一格多次运行时 `repeat` 编号从 0 重来，导致重复计数

**现象**

为做重复性分析，对 `3B_q4_k_m_ctx8192_c1` 又跑了 5 轮。之后这一格的 `repeat` 列变成：

```
[0, 0, 1, 1, 2, 2, 3, 4]
```

**根因**

`tc_run_cell.py` 每次调用都从 `repeat=0` 开始编号，不知道这一格之前跑过几轮。
于是 `(cell_id, repeat)` 重复：0/1/2 各出现两次。

**影响**

- `tc_analyze.py` 用 `.groupby(["cell_id","repeat"]).last()` 去重 → **后跑的覆盖先跑的**，
  该格实际只有 5 轮进入汇总（不是 8 轮）。这是合理行为，但要知道。
- `tc_analyze_variance.py` 原先**没有去重**，会把同一轮算两次 → CV 被低估。**已修**。

**修复**

- 方差脚本加与汇总脚本相同的 `.last()` 去重；
- 文档记下这条口径：**重复次数以「去重后的 repeat」为准，而不是行数**。

**教训**

数据里出现"看起来重复但编号不同"的行时，先问 **编号是谁生成的**。
这批数据的 `repeat` 是**局部编号**，不是全局编号——分析脚本必须自己界定"一轮"是什么。

## F13 · 2026-11-05 · 不同的混合长度分布共用 `_mix` 后缀 → 同一 id 互相覆盖

**现象**

给采集器加 `--length-mix` 后跑两组混合：
- B：`256:0.7, 1024:0.2, 2048:0.1`
- C：`128:0.5, 2048:0.5`

两次都写进了 **`3B_q4_k_m_ctx8192_c4_mix`**。分析时同一格出现两行、长度中位数一个 297
一个 1972——这才发现身份被覆盖了。

**根因**

后缀只加了常量 `_mix`，**没有把分布编码进 id**。而 cell_id 在整个项目里是"身份"：
统计、去重、绘图、claims 全都靠它。

**修复**

1. 后缀带分布指纹（sha1 前 4 位）：`_mix1d02` / `_mix5576`；
2. 行内记录 `length_mix` 原文；
3. 加守卫：同 id 若已有不同的 `length_mix`，**直接报错**而不是静默覆盖。

**教训**

> **凡是"实验参数"都必须进入 cell_id。**
> 参数变了而 id 不变，等于让两次实验共用一份档案——
> 数据不会报错，只会让后来的人看到两个互相矛盾的数。

## F12 · 2026-11-05 · 补丁脚本没验证替换是否命中，静默失败

**现象**

给 `tc_run_cell.py` 加 `--length-mix` 时，补丁脚本打印了「已加 _mix 后缀」，
但真机运行时立刻报 `NameError: name 'length_mix' is not defined`。

**根因**

补丁脚本对它要找的代码块做 `if 旧串 in 源码: 替换; 打印成功`——
但**打印在分支外面**，实际没匹配到也照打"成功"。
于是 `length_mix` 从未被定义，而作者以为改好了。

**修复**

- 插入逻辑改为对照真实函数签名（`run_cell(...)` 里加参数、`main()` 里传参）；
- 用 mock 服务跑通整条链路（10 个请求，抽样分布、nominal 字段全部正确）才收工。

**教训**

> **任何"我以为改好了"的地方，都要有断言。**
> 补丁脚本的每一次替换都必须 `assert 命中数 > 0`，
> 否则它只是让你更快地相信一个错误。

这也解释了 F13 为什么能发生：**两个 bug 是同一个心态**——
先相信"已改"，再去跑真机。

## F14 · 2026-11-05 · 多轮分支算完了却从不落盘

**现象**

`tc_run_cell.py --turns 6` 控制台完整打印了 6 轮的 TTFT/TPOT，
但紧接着 `tc.py multiturn` 说"还没有多轮数据"，`raw_cells.jsonl` 里 **0 行 `_mt`**。

**根因**

单轮路径是在 `run_cell()` 内部写盘的：

```python
finally:
    srv.stop(proc)
_append_jsonl(RAW_CELLS, rows)      # ← 单轮有
```

新增的 `run_cell_turns()` 只是 `return rows`，**没有写盘**。
于是数据只存在于内存，进程退出就没了。

**为什么之前的 mock 测试没抓到**

我验证的是"`run_turns` 会不会产出 6 行"——它确实产出了。
**但没验证"最终会不会写进原始数据"**。测试覆盖了计算，没覆盖持久化。

**修复**

补 `_append_jsonl(RAW_CELLS, rows)`，并**打印确认**：

```
已写入 6 行到 raw_cells.jsonl（每轮一行）
```

**教训**

> **"有输出"不等于"有数据"。**
> 任何新增的采集路径，验收标准必须是「文件里能查到」，而不是「屏幕上打印了」。

## F15 · 2026-11-06 · 交叉验证选错了成本列，MAPE 差 40%

**现象**

写 A2（随机重划分交叉验证）时，用"设计过的 12 格"复算，得到 **11.28%**；
而官方数字是 **8.59%**。同一份数据、同一套拟合函数，差了 40%。

**根因**

`summary_steady.csv` 里有两列成本：

| 列 | 含义 |
|---|---|
| `cost_gpu_s_per_1m` | **墙钟**口径（含收尾空闲） |
| `steady_cost_gpu_s_per_1m` | **稳态**口径（`tc_model` 实际用的目标） |

我的脚本直接读了前者——而 11.28% 正好是我们对外公布的**墙钟口径**数字。
不是算错，是**读错了列**。

**怎么发现的**

"复算值与官方不一致"这一条。**如果我第一次就用了随机划分，永远发现不了**——
因为随机划分的结果 9.96% 落在合理区间，看起来完全正常。

**教训**

> **复算必须能对上官方值，否则先别解释结果。**
> 一个"看起来合理"的数字，可能是另一套口径的正确答案。

这类错误的可怕之处：它不报错、不 nan、数量级正常，只是**换了口径**。

## F16 · 2026-11-06 · 第 7 参数修失效区：修好了但弄坏了别处

**这次不是测量错，是修法不成立。**

**动机**：四条失效证据指向同一根因，想用一个「批内 token 预算 Q」统一修正：

```
L_eff = L / (1 + (b-1)·L/Q)
```

**结果**（Q≈11.3k，落在搜索网格内部，可辨识）：

| 指标 | 基线 | 7 参数 |
|---|---|---|
| 失效区 TTFT | 81.7% | **37.4%**（−54%） |
| 混合长度 TTFT | 160.3% | **85.0%**（−47%） |
| 同族留出探针 TTFT | 13.8% | 19.1%（+39%） |
| core 留出成本 MAPE | 8.4% | 9.7%（+16%） |

**根因分析**：一个标量因子不可能同时服务「低并发正常区」和「高并发长 prompt 失效区」——
说明两者的机制不同。失效区更像是 **prefill 打断 decode 的排队效应**，
而不是「同一个摊销因子」。

**教训**

> **"能拟合失效区"不等于"模型修好了"。**
> 判据必须先写好：不只是失效区变好，而是**别处不能变差**。
> 这次先定判据（core MAPE +0.3pp 内、≥2 项改善 >20%）再算，所以能当场判"不成立"，
> 而不是自欺欺人地把 Q 报成成果。

## 1. 建实例（约 10 分钟）

```

  → 「交互式建模（DSW）」→ 「创建实例」
```

### 1.2 关键选项（**逐项对照，别改**）

| 选项 | 选什么 | 为什么 |
|---|---|---|
| 资源类型 | **公共资源** | 免费试用只在公共资源里 |

## 4. 一条命令跑完全流程（推荐）

```bash
cd ~/tokencost
bash scripts/a10_run.sh 2>&1 | tee ~/a10_full.log
```

**它会依次做 8 件事**，下面给出每件事的"预期现象"：

| 步骤 | 预期现象 | 大概耗时 |
|---|---|---|
| 0 环境 | 打印 GPU 名称与 23028 MiB | 10 s |
| 0.5 自检 | 与第 3 节相同的 `✅ 自检通过` | 1 min |
| 1 下模型 | 两个 ModelScope 下载进度条，最后 `模型下载完成` | 5–10 min |
| 2 编译 llama.cpp | 安静（输出重定向），最后进入下一步 | 8–15 min |
| 3 起服务 | 循环等 `/health`，起来了继续 | 30–60 s |
| **3.5 ctx 校验** | 打印 `日志里的 n_ctx_slot = 2304，期望 ≈ 2304` | 5 s |
| 4 标定 llama.cpp | 逐点打印并发/长度/延迟，最后 6 参数表 | 5–10 min |
| 6 起 vLLM | 打印 vLLM/torch 版本，等 `/v1/models` | 1–3 min |
| 7 标定 vLLM | 同 4 | 5–10 min |
| 8 汇总 | 一张两后端参数对照表 | 1 s |

> ⚠️ **如果第 3.5 步打印的是 `n_ctx_slot = 73728`**：说明该 build 不按并发切分 ctx，
> 脚本会自动用 `-c 2304` 重启。**看到"⚠️ 该 build 不按并发切分"是正常的，不是错误。**

## 5. 手工版（脚本某步失败时，按这里分段重跑）

脚本支持分段，先试这个：

```bash
bash scripts/a10_run.sh llamacpp    # 只跑组 ①
bash scripts/a10_run.sh vllm        # 只跑组 ②
```

仍失败时，手工执行对应片段：

### 5.1 llama.cpp 组

```bash
# 编译
cd ~/tokencost && mkdir -p ~/tc_a10/logs ~/tc_a10/results
git clone --depth 1 https://github.com/ggerganov/llama.cpp ~/tc_a10/llama.cpp
cmake -S ~/tc_a10/llama.cpp -B ~/tc_a10/llama.cpp/build -DGGML_CUDA=ON
cmake --build ~/tc_a10/llama.cpp/build -j8
ls -lh ~/tc_a10/llama.cpp/build/bin/llama-server     # 期望：文件存在、几十 MB

# 模型（ModelScope）
python3 - <<'PY'
from modelscope import snapshot_download as d
d('Qwen/Qwen2.5-3B-Instruct-GGUF', allow_patterns=['*f16*'], local_dir='/root/tc_a10/models/gguf')
d('Qwen/Qwen2.5-3B-Instruct', local_dir='/root/tc_a10/models/hf')
PY

# 起服务（73728 = 2304 × 32）
~/tc_a10/llama.cpp/build/bin/llama-server \
  -m ~/tc_a10/models/gguf/*f16*.gguf \
  --ctx-size 73728 --parallel 32 --host 127.0.0.1 --port 8090 \
  > ~/tc_a10/logs/llamacpp.log 2>&1 &

# 等健康
for i in $(seq 1 120); do curl -sf http://127.0.0.1:8090/health >/dev/null && break; sleep 2; done

# 【必做】确认每槽上下文
grep -oE "n_ctx_slot *= *[0-9]+" ~/tc_a10/logs/llamacpp.log | head -1
#   期望 ≈ 2304。若是 73728 → 杀掉重起，把 --ctx-size 改成 2304

# 标定
cd ~/tokencost/code && python3 tc_profile.py \
  --base-url http://127.0.0.1:8090/v1 \
  --spec-json ~/tc_a10/spec_gguf.json \
  --slots 32 --per-slot-ctx 2304 --gen 128 \
  --hardware "A10 24GB / llama.cpp" \
  --out ~/tc_a10/results/calib_a10_llamacpp.json
```

> `spec_gguf.json` / `spec_hf.json` 由脚本生成。手工跑时这样生成：
> ```bash
> GGUF=$(ls ~/tc_a10/models/gguf/*f16*.gguf | head -1)
> GG=$(stat -c%s "$GGUF")
> HF=$(python3 -c "import glob,os;print(sum(os.path.getsize(f) for f in glob.glob('/root/tc_a10/models/hf/*.safetensors')))")
> for pair in "spec_gguf.json:$GG" "spec_hf.json:$HF"; do
>   name=${pair%%:*}; bytes=${pair##*:}
>   cat > ~/tc_a10/$name <<JSON
> {"model":{"name":"Qwen3B","quant":"fp16","weight_bytes":$bytes,
>  "n_params":3080000000,"n_layers":36,"n_kv_heads":2,"head_dim":128}}
> JSON
> done
> ```

## 6. 怎么判断这次真的跑成功了

### 6.1 两个结果文件都存在且参数合理

```bash
cd ~/tc_a10/results
python3 -c "
import json,glob
for f in sorted(glob.glob('calib_a10_*.json')):
    d=json.load(open(f))
    print(f, '| n_points', d['n_points'], '| bw %.0f'%d['bw'], '| c_srv %.3f'%d['c_srv'],
          '| mape %.1f%%'%(d['residual'].get('mape_tpot',float('nan'))*100))
"
```

> ✅ **检查点 6**：`n_points` ≥ 6；`bw` 在 **350–550 GB/s**（A10 标称 600 的有效值）；
> `c_srv` 是**正数且 < 20 ms**。

### 6.2 验收表（写进报告用）

| 检验 | 期望 | 不符说明 |
|---|---|---|
| ① A10 的 `bw` | 350–550 GB/s | 太低 → 带宽没用满 |
| ② llama.cpp 的 `c_srv` vs 4060 的 0.766 | 差 <30% | 差很大 → `c_srv` 不是栈属性 |
| ③ vLLM 的 `c_srv` vs llama.cpp | 差 >50% | 几乎相同 → 开销同源（也是结论） |
| ④ 两后端 6 参数都能拟合 | 各自 MAPE <15% | 拟合不上 → 模型形式依赖后端 |

### 6.3 把结果带回来（三选一）

1. **JupyterLab 左侧文件树** → `tc_a10/results/` → 右键 `Download`（最稳）
2. 终端 `cat` 出参数表，整段贴回来
3. 实例能联网且有凭据：`git add -A && git commit -m a10 && git push`

## 7. 故障排查（按现象查）

| 现象 | 原因 | 处理 |
|---|---|---|
| `看不到 GPU` | 规格选错 | 换 `ecs.gn7i-c8g1.2xlarge` |
| 下载模型卡住 | ModelScope 限速/网络 | 重试；或 `pip install -q modelscope -U` |
| 编译报 `nvcc not found` | 镜像没 CUDA | 换 PyTorch+CUDA 镜像，或 `apt-get install -y nvidia-cuda-toolkit` |
| `llama-server` 起不来，日志 `failed to allocate` | KV 太大（ctx 语义不切分） | 把 `--ctx-size` 改成 2304 |
| 健康检查 120 次都没过 | 端口占用 | `pkill -f llama-server`；换端口 8091 |
| 标定报 `prompt 超长` | PER_SLOT < 2048+128 | 用 2304，不要 2112 |
| TTFT 不随长度增长 | **缓存命中**（F9） | `tc_profile` 已加 nonce；若仍如此，查服务端日志 |
| vLLM 报 `CUDA driver version is insufficient` | 镜像 CUDA 太旧 | 换镜像；或 `pip install -q "vllm==0.6.*"` |
| 标定中途 `Killed` | 显存不足 | 降 `--max-num-seqs` 到 16，并在报告里注明 |
| 实例被回收 / 断连 | 免费额度用尽或超时 | 结果文件在 `~/tc_a10/results/`，重连后先 `ls` 确认还在 |

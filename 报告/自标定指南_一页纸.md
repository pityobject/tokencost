# 在你自己的机器上标定（一页纸）

> 这份文档回答一个问题：**我没有 RTX 4060，这套方法还能用吗？**
> 能。模型是通用的，6 个参数需要在你自己的栈上重新量一遍。下面是完整流程。

---

## 一、先量什么（10 分钟机器时间）

你只需要 8 个配置点。**关键不是点数，是并发档的跨度**——下面的对比是实测的：

| 测量计划 | 格数 | 留出中位误差 | `c_srv` 偏差 |
|---|---|---|---|
| 随便挑 4 个 | 4 | **20.0%** | +122% |
| 设计过的 8 个（2 模型 × 4 档并发） | 8 | **10.6%** | +23% |
| 仓库实际用的 12 个（+多上下文/多量化） | 12 | **8.1%** | 基准 |

**为什么"随便 4 个"不行**：并发只有 1 和 8 两档时，
"每流每步的服务开销 `c_srv`" 与 "首字固定开销 `ovh`" 在数学上**无法分辨**——
它们会互相抵消，拟合出一个看着合理但完全错位的组合。

### 推荐的 8 格

| 维度 | 取值 |
|---|---|
| 模型 × 量化 | 2 个（建议同一模型的两个量化档，或两个尺寸） |
| 并发 | **1 / 4 / 16 / 32**（四档必须都有） |
| 上下文上限 | 足够装下你的 prompt × 最大并发（如 512 × 32 = 16384） |
| 提示长度 | 至少**两个**不同长度（如 512 与 2048），用来确定 prefill 斜率 |

> ⚠️ 注意：`ctx=2048 × 并发 32 = 65536` 超过 Qwen2.5 原生 32768，**这种格物理上不可行**。
> 高并发必须配小 ctx。

## 二、量完填一份 JSON

```json
{
  "hardware": "RTX 4090 24GB",
  "backend": "llama.cpp b11669",
  "model": {
    "name": "mymodel", "quant": "q4_k_m",
    "weight_bytes": 2104932768,
    "n_params": 3090000000,
    "n_layers": 36, "n_kv_heads": 2, "head_dim": 128
  },
  "measurements": [
    {"ctx": 512, "conc": 1,  "prompt_tokens": 512, "ttft_ms": 78.0,  "tpot_ms": 9.7},
    {"ctx": 512, "conc": 4,  "prompt_tokens": 512, "ttft_ms": 96.0,  "tpot_ms": 12.9},
    {"ctx": 512, "conc": 16, "prompt_tokens": 512, "ttft_ms": 260.0, "tpot_ms": 25.0},
    {"ctx": 512, "conc": 32, "prompt_tokens": 512, "ttft_ms": 480.0, "tpot_ms": 39.5}
  ]
}
```

字段从哪来：

| 字段 | 怎么取 |
|---|---|
| `weight_bytes` | GGUF 文件字节数（多分片求和）——**实测文件大小，不要按参数量估** |
| `n_params` / `n_layers` / `n_kv_heads` / `head_dim` | GGUF metadata（`llama.cpp` 的 `--print-model-info`）或 HuggingFace `config.json` |
| `ttft_ms` / `tpot_ms` | 你已有的压测工具输出即可；用**中位数**，别用平均值 |

## 三、一条命令

```bash
python code/tc_calibrate.py my_measurements.json
python code/tc_recommend.py --calib results/calib_mymachine.json --ttft 600 --tpot 60
```

输出会告诉你：

- 拟合出的 6 个参数
- 每个测量点的残差（**如果 >15%，说明输入数据有问题，别急着相信结果**）
- 自由度够不够（8 观测 − 6 参数 = 2，勉强够；建议 10 个点以上）

## 四、一个必须知道的坑：`PEAK_dec` 可能不可识别

decode 算力只有在**算力受限**时才能从数据里反推出来。
消费级 GPU 跑小模型时，decode 几乎总是**访存受限**（权重读得慢），
于是 `PEAK_dec` 在数学上没有约束——拟合会给出一个荒唐值（比如 163 TFLOP/s）。

**这不是 bug，是这类模型的普遍性质**。处理办法：

- 拟合结果里 `PEAK_dec` 明显偏离硬件规格（比如超出 2 倍）→ **当作不可识别**，不要引用；
- 它对预测几乎没有影响（因为那个分支从不被触发），但要如实标注。

同理，`ovh_ttft` 在本项目里的置信区间宽达 **141%**——它影响小、难测准，
属于"估不准但不影响选谁"的参数。

## 五、你需要知道的方法边界

| 边界 | 说明 |
|---|---|
| 单卡、单机 | 模型是单卡 roofline，不覆盖多卡/集群 |
| 同步波次 | 真实泊松到达下 TTFT 会差一个量级（容量只能给上界） |
| 一个后端 | `c_srv` 是**部署栈属性**，换 vLLM/SGLang 必须重新标定 |
| 质量轴 | 质量基准要在你的业务数据上重做——仓库里的 400 题只代表算术/格式/推理三族 |

**这套方法的定位**：不是"通用性能数据库"，而是
**"给你一台机器、一套栈，30 分钟算出它能不能满足你的 SLA，以及最便宜的合规配置"**。

## 三之二、更省事的方式：一条命令

如果不想手工填 JSON，`tc_profile.py` 会自己发请求：

```bash
# 指向任何 OpenAI 兼容端点（llama.cpp / vLLM / SGLang / TGI / Ollama）
python code/tc_profile.py \
  --base-url http://127.0.0.1:8080/v1 \
  --spec 3B:q4_k_m \
  --out results/calib_profile.json

python code/tc_recommend.py --calib results/calib_profile.json --ttft 600 --tpot 60
```

默认测量计划 8 格（并发 1/4/16/32 + 长度 128/512/2048），约 5–10 分钟。

它会自动：

- 探测 `/v1/models`（不存在也能继续，用 `--wire-model` 指定）
- 流式测 **TTFT**（首 token 时间）与 **TPOT**（后续每 token 时间）
- 拟合 6 参数、打印每个测量点的残差
- **检查 `decode 算力` 是否可识别**（不可识别会明确警告，不给你一个假数字）

先验证工具本身（不需要服务器）：

```bash
python code/tc_profile.py --selftest
```

用仓库标定值合成带噪数据再拟合回去，关键 4 个参数误差应 < 15%。

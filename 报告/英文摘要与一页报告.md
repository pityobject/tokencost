## A. Abstract（3–5 句，可直接用）

> I built a six-parameter analytical model that predicts the **cost and latency of LLM
> inference** on a single 8 GB consumer GPU. I measured **100 configurations and 300
> session-level runs** across five model/quantization combinations, three context sizes
> and eight concurrency levels, then calibrated the model on 12 cells and validated it on
> **68 held-out configurations**: unit-cost MAPE is **8.70%** overall and **5.8%** on the
> concurrency levels covered by calibration. The central finding is that beyond
> ~8 concurrent requests the bottleneck moves off the GPU: **57% (up to 77%) of
> inter-token latency at high concurrency is per-step overhead inside the decode loop**,
> while HTTP/SSE delivery contributes **≈ 0 ms**. I verified the bottleneck three
> independent ways (pure-backend ceiling, the fitted overhead term, and a 0.5B model that
> saturates while still 9.5× away from its compute bound), and I explicitly mapped where
> the model must not be trusted — it is **family-agnostic (11.6% cost MAPE on Llama-3.2-1B with
> zero refitting)**; its capacity estimate is an upper bound (measured 72% of predicted,
> 88% once prefill interference is included), and queueing delay is only order-of-magnitude.

## C. One-page report (English, for a take-home or poster)

### Problem

Decoding a token requires streaming the entire model from VRAM, so serving cost is set by
bandwidth and compute — but real deployments rarely reach those limits. **Which
(model size, quantization, context limit, concurrency) should you deploy for a given SLA,
quality floor and hardware budget?**

### Method

```
TPOT(b) = max( (W + KV·L·b)/BW , 2·P·b/PEAK_dec ) + c_srv·b
TTFT(L) = max( W/BW , 2·P·L·min(b,B_SAT)/PEAK_pre ) + c_srv·b + ovh
cost    = 1e6 / ( b·GEN / (TTFT + GEN·TPOT) )        [GPU·s per 1M tokens]
```

Fitted parameters: **BW = 249.1 GB/s**, **PEAK_dec = 13.2 TFLOP/s**,
**PEAK_pre = 31.9 TFLOP/s**, **c_srv = 0.766 ms/stream/step**, **B_SAT = 13.3**,
**ovh = 15.96 ms**. Calibration used 12 cells; the split was fixed before any measurement.

### Results

| | |
|---|---|
| Held-out cost MAPE (68 cells) | **8.70%** |
| Held-out MAPE on calibrated concurrency (33 cells) | **5.8%** |
| 90% interval coverage | 86.8% |
| Cross-family (Llama-3.2-1B, zero refit) | **11.6%** cost MAPE |
| Decision regret vs post-hoc optimum | 3.3% |

### The finding

At concurrency ≥16, GPU utilization falls from 89% to 48% while throughput still rises.
Backend-only benchmarking shows the serving path reaches **40–48%** of the hardware
ceiling, and comparing server-reported eval time against client-measured latency shows
**delivery overhead ≈ 0**. The loss is per-step work inside the decode loop
(sampling, batch construction, slot scheduling) — a scheduling problem, not a
networking one.

### Where it must not be used

Poisson-arrival experiments show measured TTFT is **2–8×** the model's prediction,
because the model computes *service time*, not *queueing time*. Synchronized-wave
measurements are the **optimistic** case, not the worst case.

## D. 30-second spoken intro

> I wanted to know what actually determines the price of one million tokens.
> It turns out the GPU is not the limit. On an 8 GB card I measured 100 configurations and
> found that past roughly eight concurrent requests, most of the response delay is
> overhead *inside* the inference loop — not memory, not the network. I built a
> six-parameter model that predicts cost within 5.8% on calibrated configurations, and I
> documented exactly where it breaks: it transfers to a different model family for free,
> but not to a different arrival pattern, because it models service time and not queueing.
